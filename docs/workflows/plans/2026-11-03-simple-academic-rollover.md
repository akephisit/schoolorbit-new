# Simple academic rollover implementation

The user approved the design in [the scoped specification](../specs/2026-11-03-simple-academic-rollover-design.md). This plan records execution ownership, not another approval gate.

1. Backend owns migration 152, the canonical roster preview/confirm DTOs and services, existing lifecycle/Core/Students changes, HTTP/OpenAPI composition and generated artifacts. Remove Results prerequisites at their authoritative readiness/command owners. Preserve the existing receipt ledger, making absent manual-policy/recommendation evidence explicit. Reject stale or overlapping commands and preserve replay identity. Prepare destination memberships with an explicit effective date; never activate implicitly.
2. Data/Migration owns migration 153, new Lifecycle retention model/service files, new application adapter and domain-provider files, and this design/plan. Shared existing module registration, routes, dependencies and runtime hooks remain Backend-owned and are integrated from an explicit handoff. Implement disabled/future-only policy, whole-term latest-boundary preview, durable jobs and actual provider execution, retaining aggregate summaries and physical deletion progress. Do not execute existing-tenant cleanup.
3. Frontend owns the unified year-lifecycle page and generated-contract consumers after the API boundary stabilizes. Include year/term setup, next-term continuity, roster preview and one confirmation, prepared-state outcome, and a separate retention section with actual eligibility/scope messaging. Score reset remains separate. Preserve denied, loading, stale and pending states.
4. Backend runs focused owner tests and the sole shared Cargo build. Data/Migration adds focused retention deadline, policy, durable progress and preservation cases in new owned test files. Use isolated synthetic databases under the repository fixture runner. Frontend runs scoped type/static and interaction checks. Generated contracts, permissions, migration preservation and architecture checks follow the affected-owner matrix in `.rules` and recipes in `docs/TESTING.md`.
5. Record durable lifecycle/retention semantics in `.rules` and deployment/recovery behavior in `docs/OPERATIONS.md`. Do not add another documentation owner or change applied migration history.
6. Senior integrates the complete candidate, freezes source, and assigns independent Reviewer and QA. Fix findings through their owners and repeat affected checks. Senior owns Git, draft PR/checkpoints and authorized integration/deployment; feature deployment never authorizes existing-tenant destructive cleanup.

Required regression cases: all manual outcomes; no locked-results/credits prerequisite; same-year roster unchanged; explicit effective date and prepared destination; actor/tenant denial; duplicate request replay and mismatched replay refusal; stale/concurrent confirmation; legacy executing receipt overlap; year/term reopen dependencies; policy disabled and historical exclusion; primary/secondary/mixed/unknown level eligibility; grace after actual latest close; disable and reopen before worker acceptance; Attendance source/notification queue refusal; retained school/teacher summaries; unchanged Behavior totals and cycles; resumed chunk work; Files pending/failed object reconciliation; no mutation from GET.
