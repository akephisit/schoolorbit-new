# แผนลดความซับซ้อนงานวิชาการหลังจัดหลักสูตร

สถานะ: ผู้ใช้อนุญาตให้เริ่มพัฒนาแล้วหลังตกลงย้ายข้อมูลปัจจุบันและลบฉบับเก่า
วันที่: 14 พฤศจิกายน 2569 (2026-11-14) เขตเวลา Asia/Bangkok

## จุดประสงค์และขอบเขตงาน

ลดทั้งขั้นตอนที่คนใช้ต้องทำและโครงสร้างภายในระบบ ตั้งแต่เปิดสอน จัดตารางเรียน จัดสอบ ไปจนถึงข้อมูลที่นำไปเช็คชื่อและประเมินผล
เอกสารนี้เป็นแผนดำเนินงานตามทิศทางที่ผู้ใช้อนุมัติ โดยใช้ [แบบระบบปัจจุบัน](../specs/2026-11-14-academic-current-operations-design.md) เป็นข้อตกลงการออกแบบ
การย้ายและลบข้อมูลจริงต้องผ่าน audit การตรวจรับ และขั้นตอน release ที่ประสานกัน ไม่ลบข้อมูล production ทันทีจาก checkpoint เอกสารนี้

## เรื่องที่ตกลงแล้ว

- ในภาคเรียนที่เลือก มีชุดเปิดสอนปัจจุบันชุดเดียว ครอบคลุมรายวิชาและกิจกรรมที่เปิดจริง
- มีตารางเรียนปัจจุบันชุดเดียวต่อภาคเรียน แก้แล้วบันทึกลงชุดนั้นโดยตรง
- มีตารางสอบปัจจุบันชุดเดียวต่อรอบสอบ เช่น กลางภาคและปลายภาคเป็นคนละรอบ ไม่ใช่คนละเวอร์ชัน
- ตัดเวอร์ชันทางธุรกิจ ประวัติการแก้ไข และขั้นตอนสร้างร่าง คัดลอก ออกฉบับ และเผยแพร่ออกจากสามงานนี้
- ภายในต้องเรียบง่ายตามหน้าจอด้วย ไม่ซ่อนการสร้างเวอร์ชันอัตโนมัติไว้เบื้องหลัง
- ย้ายสถานะใช้งานปัจจุบันที่เลือกแล้วเข้าโครงสร้างใหม่ จากนั้นลบเวอร์ชัน ร่าง snapshot และ journal เก่าที่เป็นของกลไกฉบับที่เลิกใช้จริง เมื่อยืนยันการแปลงครบแล้ว
- ไม่เก็บประวัติแฝงในตารางเก่า ข้อมูลที่ทำ soft delete ก้อนข้อมูลประวัติ หรือ archive และไม่ให้ runtime ย้อนอ่านฉบับเก่า
- การลบนี้ครอบคลุม Delivery, Timetable และสิ่งตกค้างจากการเผยแพร่ตารางสอบที่เลิกใช้ตามผลตรวจ ไม่รวมฉบับทะเบียน/หลักสูตรหรือประวัติ Results ทั้งระบบ
- ไม่ต้องมีขั้นตอนอัปเกรดแหล่งเปิดสอนของตารางเรียน
- การลบรายการเปิดสอนของภาคเรียน ลบข้อมูลเช็คชื่อและคะแนนวิชาการที่เกี่ยวข้องได้ แม้กรอกไปแล้ว
- ไม่เพิ่มคุณสมบัติย้อนคืนหรือเก็บประวัติเพื่อกู้รายการเปิดสอนที่ผู้ใช้ตั้งใจลบ
- ยังรักษาการแยกโรงเรียน การตรวจสิทธิ์ รหัสรายการและความสัมพันธ์เดิมที่ยังมีความหมาย
- ยังตรวจ revision ของแถวเพื่อกันการบันทึกทับกัน ค่านี้เป็นกลไกทางเทคนิค ไม่ใช่เวอร์ชันย้อนหลัง
- ทะเบียนรายวิชา ทะเบียนกิจกรรม และฉบับหลักสูตรเป็นขอบเขตต้นน้ำของตนเอง ไม่ถูกยุบฉบับตามงานเปิดสอน

## ข้อตกลงใช้งานสำหรับการพัฒนา

- ใช้ปีและภาคเรียนที่ผู้ใช้เลือกอย่างชัดเจน ไม่เดาบริบทจากวันที่
- ให้ปุ่มบันทึกเป็นจุดยอมรับการแก้ไข พร้อมแจ้งข้อผิดพลาดในรายการที่แก้
- แยกปุ่มลบรายการเปิดสอนออกจากการแก้ครู เวลา ห้อง หรือกลุ่มเรียน
- ก่อนยืนยันลบ แสดงภาคเรียน รายการ และจำนวนข้อมูลเกี่ยวข้องที่กำลังจะหาย
- การแก้โดยตรงใช้สิทธิ์ Manage ของรายการตาม scope เดิม ส่วนคำสั่งลบข้อมูลเกี่ยวข้องต้องมีสิทธิ์ระดับโรงเรียน; สัญญาสิทธิ์ที่แน่นอนยืนยันหลัง audit
- ภาคเรียนที่ปิดแล้วยังคง lifecycle guard เดิม งานนี้ไม่เปิดปีหรือภาคเรียนกลับมาโดยอัตโนมัติ

## ภาพการทำงานปัจจุบันและเป้าหมาย

ปัจจุบัน Delivery และ Timetable มีกราฟฉบับ ร่าง การเผยแพร่ และการเลือกข้อมูลตามวันที่
ตารางเรียนยังผูกแหล่งเปิดสอนและตรวจการปรับแหล่งนั้น ส่วนตารางสอบมีขั้นตอนเผยแพร่ของตนเอง
รายละเอียดอ้างอิงจาก [Delivery](../../../backend-school/crates/school-academic-delivery/src/services/change_sets.rs), [Timetable](../../../backend-school/crates/school-academic-timetable/src/services/timetable_version_service.rs) และ [ตารางสอบ](../../../backend-school/crates/school-academic-assessment/src/exam_schedule/services/publishing.rs)

เป้าหมายการใช้งาน:

1. เลือกปีและภาคเรียน
2. เลือกรายวิชาหรือกิจกรรมจากทะเบียนและหลักสูตร แล้วกำหนดกลุ่ม นักเรียน และครู
3. บันทึกชุดเปิดสอนปัจจุบัน
4. วางคาบเรียน ตรวจชน แล้วบันทึกตารางเรียนปัจจุบัน
5. เลือกรอบสอบ วางวิชา เวลา ห้อง และผู้คุม แล้วบันทึกตารางสอบของรอบนั้น
6. เช็คชื่อ กรอกคะแนน และอ่านรายงานจากข้อมูลปัจจุบันตามสิทธิ์

การแก้ครูหรือย้ายคาบเป็นการแก้ข้อมูล ไม่ใช่คำสั่งลบคะแนนหรือเช็คชื่อ
หากการแก้ทำให้ข้อมูลเดิมไม่สอดคล้อง ต้องกำหนดการตรวจและการแจ้งเตือนแยกต่างหาก ไม่ลบข้อมูลเงียบ ๆ

ต้องตามผู้เรียกใน [งาน promotion เดิม](../../../backend-school/crates/school-academic-lifecycle/src/services/promotion_run_review.rs) และแยกจากกระบวนงานปัจจุบันก่อนเปลี่ยนข้อมูล

Lifecycle ปัจจุบันปิดช่วงการศึกษาโดยตรงและให้เจ้าหน้าที่เลือกการขึ้นปีใหม่เอง
ผลที่ล็อก หน่วยกิตรายปี และนโยบายเลื่อนชั้นไม่ใช่เงื่อนไขก่อนปิดหรือย้ายรายชื่อขึ้นปีแบบนี้
การลบผลวิชาไม่หมายถึงย้อนการย้ายห้อง ขึ้นปี จบการศึกษา หรือย้ายออกที่ยืนยันไปแล้วโดยอัตโนมัติ
อ้างอิง [คำสั่งขึ้นปีปัจจุบัน](../../../backend-school/crates/school-academic-lifecycle/src/services/year_rollover_command.rs) และ [กติกาปัจจุบัน](../../../.rules)

## ขอบเขตคำสั่งลบรายการเปิดสอน

ให้คำสั่งระบุโรงเรียน ภาคเรียน และรายการเปิดสอนที่เลือกอย่างแน่นอน แล้วหาลูกของรายการนั้นผ่านรหัสจริง
การลบกลุ่มย่อยต้องกำหนดขอบเขตลูกของกลุ่มนั้นให้ชัด ไม่ถือว่าเป็นการลบทั้งภาคเรียน

| ข้อมูล         | ขอบเขตที่เสนอให้คำสั่งลบจัดการ                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------- |
| เปิดสอน        | รายการของภาคเรียนที่เลือก พร้อมกลุ่ม สมาชิก และการมอบหมายครูที่รายการนั้นเป็นเจ้าของ               |
| ตารางเรียน     | เฉพาะคาบและลูกที่อ้างรายการ/กลุ่มที่ลบ ไม่ลบตารางของวิชาอื่น                                       |
| ตารางสอบ       | เฉพาะวิชาสอบ การจัดห้อง ผู้เข้าสอบ และผู้คุมส่วนที่เป็นของวิชานั้น                                 |
| เช็คชื่อรายคาบ | lesson sessions, records และหลักฐาน/สรุปที่เป็นของคาบที่ลบ ตามเจ้าของข้อมูล                        |
| ประเมินผล      | โครงสร้างคะแนน รายการคะแนน คะแนนจริง ผลประเมิน ผลรายวิชา/กิจกรรม และการยืนยันที่เกี่ยวข้อง         |
| ผลรวม          | ตัดส่วนร่วมของวิชาที่ลบออกจาก GPA หน่วยกิต และผลรวมภาค/ปี รวมข้อมูลสรุปที่บันทึกค้างไว้            |
| ผู้อ่านอื่น    | ล้างหรือปรับข้อมูลอนุพันธ์ แคช และสิทธิ์เข้าถึงที่อ้างรายการนั้น ไม่ปล่อยให้ URL เก่าคืนข้อมูลค้าง |

ห้องสอบรวมและบล็อกกลางต้องเหลือส่วนที่วิชาอื่นยังใช้ ไม่ลบทั้งห้องหรือทั้งรอบตามความสะดวก
แยกการลบข้อเท็จจริงทางวิชาการจากการลบไฟล์จริง หากมีไฟล์ ให้ Files จัดการตามขอบเขตและการอ้างอิงของตน
คำสั่งข้อมูลต้องเป็นธุรกรรมเดียวข้ามเจ้าของที่เกี่ยวข้อง หรือระบุขอบเขตการเก็บกวาดไฟล์ภายนอกให้ชัดเจน
ยังต้องออกแบบเจ้าของคำสั่ง สิทธิ์ลบ ลำดับล็อก การตรวจ revision และผลลัพธ์เมื่อคำขอเดิมถูกส่งซ้ำ

สิ่งที่ไม่รวมในคำสั่งลบนี้:

- รายการเปิดสอนหรือภาคเรียนอื่น รวมถึงข้อมูลโรงเรียนอื่น
- การมาโรงเรียนรายวันและการเช็คชื่อพิเศษที่ไม่ใช่ลูกของรายวิชานั้น
- นักเรียน ครู ห้องจริง รายชื่อรายปี และการจัดชั้น/ห้องที่มีเจ้าของแยกต่างหาก
- ทะเบียนรายวิชา ทะเบียนกิจกรรม ฉบับหลักสูตร และตารางคาบมาตรฐานที่ใช้งานร่วมกัน
- ผลนิเทศจริง คะแนนพฤติกรรมที่กรอกเอง และข้อมูลอื่นที่ไม่ใช่ลูกของรายการนั้น; ตัดการอ้างอิงนิเทศและกลับเฉพาะส่วน Behavior จาก Attendance ตามแบบ

## การย้ายข้อมูลเดิมและลบ version เก่า

การลบประวัติฉบับเก่าหลังแปลงสำเร็จเป็นข้อสรุปแล้ว เรื่องที่ยังต้องเลือกคือข้อมูลใดเป็นสถานะปัจจุบันเมื่อกราฟเดิมขัดกัน
ข้อเสนอเริ่มต้นคือใช้สถานะที่ใช้งานจริง ณ จุดเปลี่ยนระบบ โดยกำหนดกติกาเลือกที่ตรวจสอบได้สำหรับแต่ละบริบท
ไม่ถือว่าร่างล่าสุด เลขเผยแพร่สูงสุด หรือแผนอนาคตคือสถานะใช้งานจริงเสมอ
ตัวเลือกเริ่มต้นของหน้าจอก็ไม่ใช่หลักฐาน: `selectDeliveryVersion` ปัจจุบันเลือก draft ก่อน จึงต้องตรวจแหล่งและการใช้งานจริงด้วย

- แปลงแยกตามโรงเรียน ปี และภาคเรียน ให้เหลือชุดปัจจุบันหนึ่งชุดต่อบริบท และตารางสอบหนึ่งชุดต่อรอบสอบ
- การลบฉบับเก่าไม่ได้อนุญาตให้ทิ้งทั้งภาคเรียน ปี หรือโรงเรียนอื่น ต้องรักษาบริบทเหล่านั้นแยกกัน
- รักษารายการเปิดสอน กลุ่ม ครู นักเรียน และการจัดกลุ่ม/ห้องที่ยังใช้งาน พร้อมเช็คชื่อ คะแนน และผลที่ยังเกี่ยวข้อง
- แม้ข้อมูลที่ต้องเก็บอ้าง UUID ของฉบับเก่าอยู่ ต้องย้ายความสัมพันธ์ไปยังโครงสร้างใหม่ก่อน โดยรักษารหัสที่ยังมีความหมาย
- ห้ามลบทะเบียนหรือรายการร่วมที่ยังใช้อยู่เพียงเพราะลบตัวครอบฉบับเก่า
- ทรัพยากรที่อยู่เฉพาะกราฟที่ทิ้งและไม่มีในชุดปัจจุบันที่เลือก ลบพร้อมข้อมูลเกี่ยวข้องได้ตามขอบเขตลบรายการเปิดสอนที่ตกลงแล้ว
- รักษาผลนิเทศจริงโดยตัดการอ้างอิงปฏิบัติการที่ถูกลบ และกลับเฉพาะส่วน Behavior จาก Attendance ของคาบที่ลบผ่าน provider เดิม ไม่แตะคะแนนกรอกเอง
- เมื่อพิสูจน์จำนวน รหัส ความสัมพันธ์ และข้อมูลปัจจุบันที่ต้องเก็บได้ครบ จึงสลับใช้โครงสร้างใหม่และลบข้อมูลกลไกฉบับที่เลิกใช้ใน cutover เดียวกัน
- ไม่คงเจ้าของ runtime สองชุดหรือ fallback ถาวร และไม่สร้างระบบวันที่ใหม่เพื่อเลือกฉบับแทน

การออกแบบต้องตรวจ migration timeline ทั้งชุดก่อนระบุ SQL หรือความสัมพันธ์ที่จะลบ ไม่ใช้ blanket CASCADE แทนการตรวจขอบเขต
ไฟล์ SQL migration ที่ใช้แล้วคงเดิมในฐานะบัญชีการติดตั้ง การลบเวอร์ชันธุรกิจไม่อนุญาตให้แก้ไฟล์เหล่านั้น
checkpoint เอกสารนี้ยังไม่มีการแปลงหรือลบข้อมูลจริง การดำเนินงานตามแผนใช้ migration และ release gates ที่ตรวจสอบได้

## ข้อตกลงเพิ่มเติมและรายละเอียดที่ต้องตรวจให้ครบ

- การเลือกข้อมูล active context ใช้ publication ที่ใช้งานจริง ณ cutover ตามวัน Bangkok ไม่ใช้ร่างที่ UI เลือกหรือเลขสูงสุดโดยอัตโนมัติ
- บริบทอื่นต้องรักษาหนึ่งชุดต่อภาคเรียน; กติกา executable สำหรับ draft-only/ภาคเรียนยังไม่เปิดเป็นงาน audit และหยุดเมื่อเลือกไม่ได้อย่างแน่นอน
- วันเก่าที่มี Attendance facts แล้วคงข้อเท็จจริงนั้น; วันที่ยังไม่เคยสร้างคาบไม่สามารถอ้างว่าเป็นตารางเก่าที่สร้างกลับมาได้
- ไม่เพิ่ม effective-date engine การตั้งเวลาเปลี่ยนฉบับ หรือการอนุมานภาคเรียนจากวันที่
- ผลนิเทศจริงคงไว้ ตัดเฉพาะการอ้างอิงปฏิบัติการที่ถูกลบ และให้ผู้อ่านรองรับแหล่งที่หาย
- กลับเฉพาะคะแนน Behavior ที่มาจาก Attendance ของคาบที่ลบผ่าน provider เดิม คะแนนกรอกเองไม่เปลี่ยน
- Results คงประวัติ revision นโยบายและ locks ของตน แต่ลบส่วนร่วม/คะแนนของรายการที่ลบและปรับผลรวมที่บันทึกไว้ให้สอดคล้อง
- การแจ้งเตือนผู้รับเลื่อนไว้จนตกลงเหตุการณ์ ผู้รับ และการรวมข้อความ ใช้ realtime เดิมปรับหน้าจอปัจจุบัน ไม่มีข้อความภายนอกในระยะนี้

## เจ้าของระบบและข้อตกลงการออกแบบ

Delivery เป็นเจ้าของชุดเปิดสอน Timetable เป็นเจ้าของคาบ และ Assessment เป็นเจ้าของตารางสอบ/คะแนนตามขอบเขตเดิม
Results, Attendance, Supervision และ Behavior ต้องให้บริการจัดการข้อมูลของตนผ่าน public provider ที่แคบและมีชนิดชัดเจน
คำสั่งข้ามโดเมนประกอบในชั้น application ตาม dependency เดิม ไม่สร้างแพลตฟอร์มทั่วไปเพื่อรองรับงานนี้
ตัวอย่างขอบเขตเดิม: [Delivery ports](../../../backend-school/crates/school-academic-delivery/src/ports.rs), [Attendance sessions](../../../backend-school/crates/school-attendance/src/services/sessions.rs), [Behavior adapter](../../../backend-school/src/adapters/behavior.rs)
สิทธิ์ครูและผู้ประสานงานต้องอ่านชุดปัจจุบันร่วมกัน โดยยังรักษาขอบเขต school/organization/assigned/own ที่มีอยู่
Transport ใช้เจ้าของ `school-academic-{core,delivery,assessment,timetable,results,lifecycle}-http` และสัญญาที่สร้างจาก Rust ตามปกติ

`.rules` ปัจจุบันยังบังคับ publication ที่แก้ไม่ได้ ประวัติ แหล่งตารางเรียน และข้อห้ามลบบางกรณี
ต้องแก้กติกาเหล่านี้ประสานกับ implementation และสัญญาใหม่ก่อน cutover
แบบเดิมเป็นข้อมูลพื้นหลัง ยังไม่ได้ถูกเปลี่ยนหรือประกาศว่าเลิกใช้จากเอกสารฉบับนี้

## ลำดับดำเนินงาน

1. บันทึกแบบที่อนุมัติและตรวจ audit migration/ผู้ใช้ข้อมูลให้ครบ โดยไม่เพิ่มคิวขออนุญาตสำหรับข้อตกลงที่สรุปแล้ว
2. ตรวจ migration timeline ทั้งชุดและข้อมูลเดิม พร้อมตามผู้เขียน/ผู้อ่านจริงก่อนออกแบบการแปลง
   ยังไม่เสนอชื่อคอลัมน์ ตาราง หรือ SQL migration แบบเจาะจงจากการอ่านบางส่วน
3. ออกแบบบริการ API และพื้นที่เก็บข้อมูลปัจจุบันที่เป็นแหล่งจริงชุดเดียว พร้อมแก้ `.rules` ที่ขัดกันในงานเดียวกัน
   รักษารหัสและความสัมพันธ์ที่ยังมีความหมาย ไม่สร้างประวัติปลอมเพื่อผ่าน constraint เดิม
4. วางการแปลงข้อมูลและ reconciliation ให้พิสูจน์สถานะที่เลือก รหัส จำนวน และความสัมพันธ์ของข้อมูลปัจจุบันที่ต้องเก็บ รวมกรณีแปลงไม่ได้
   ห้ามแก้ migration ที่ใช้แล้ว และห้ามสลับผู้อ่านหรือล้างของเดิมก่อนหลักฐานครบ
5. ทำ Delivery ให้แก้โดยตรง แล้วเปลี่ยน Timetable ตารางสอบ และผู้ใช้งานต่อเนื่องตามลำดับ dependency
   เมื่อการแปลงผ่าน ให้ cutover ใช้เจ้าของปัจจุบันชุดเดียวและลบแถว/สิ่งตกค้างของกลไกฉบับเก่าพร้อมเลิกผู้อ่านเดิม ไม่คงแหล่งจริงคู่ขนาน
6. เปลี่ยน frontend ไปสัญญาปัจจุบัน แล้วทำคำสั่งลบข้ามเจ้าของ ล้างข้อมูลอนุพันธ์และผลรวม ป้องกันงานค้าง/คำขอเก่าทำข้อมูลกลับมา
   สร้าง API contracts จาก Rust และปรับ tests ที่เปลี่ยนความหมายโดยมีเหตุผล พร้อมรักษาความครอบคลุมที่ยังจำเป็น
7. เลื่อน delivery messaging ไว้จนตกลงเหตุการณ์และผู้รับ โดย Notifications คงเป็นเจ้าของการส่ง; realtime เดิมยัง invalidate หน้าจอ
8. ซ้อม migration แยก fixture ตรวจทุก owner ที่เกี่ยวข้อง แล้วให้ Reviewer และ QA อิสระตรวจ candidate ที่ freeze
   Senior บันทึก draft PR checkpoints และประสาน maintenance release ที่ผ่าน gates พร้อมจุดห้ามใช้โปรแกรมเก่าหลังแปลงข้อมูล
   รายละเอียดการปล่อยและการกู้ระบบให้ไปอยู่ใน [Operations](../../OPERATIONS.md) เมื่อถึงงานพัฒนา

## เกณฑ์ตรวจรับที่ควรใช้เมื่อพัฒนา

- เพิ่มและแก้แล้วบันทึกได้โดยไม่สร้างร่าง ฉบับ หรือขั้นตอนเผยแพร่แฝง
- กลางภาคและปลายภาคมีตารางของตนเอง โดยไม่กลายเป็นกลไกเวอร์ชัน
- ลบรายการเปิดสอนที่มีคะแนนและเช็คชื่อแล้วได้ครบตามขอบเขตที่ยืนยัน
- ไม่เหลือ GPA หน่วยกิต ยอดรายงาน หรือสรุป Attendance ที่เก็บไว้จากรายการที่ลบ
- ไม่เสียข้อมูลวิชา ภาคเรียน โรงเรียน หรือทะเบียนต้นน้ำอื่น และห้องสอบรวมยังใช้งานกับวิชาที่เหลือได้
- ล้มเหลวระหว่างลบแล้วไม่เกิดข้อมูลครึ่งชุด; ไฟล์ภายนอกมีขอบเขตและวิธีเก็บกวาดที่ตรวจสอบได้
- งานเบื้องหลัง คำขอเก่า และการส่งซ้ำไม่สร้างข้อมูลที่ลบแล้วกลับมา
- การบันทึกชนกันและการบันทึกแข่งกับการลบมีผลแน่นอน ไม่เขียนทับหรือชุบข้อมูลกลับ
- เปลี่ยนครูแล้วสิทธิ์ดู/แก้/ยืนยันปรับถูกต้อง และไม่ลบคะแนนด้วยเหตุเปลี่ยนครูเพียงอย่างเดียว
- URL และผู้ใช้งานต่อเนื่องรับกรณีรายการหายได้โดยไม่แสดงข้อมูลค้างหรือเปิดเผยข้อมูลเกินสิทธิ์
- ยังตรวจครู ห้อง และนักเรียนชนกัน ทั้งตารางเรียนและตารางสอบ
- การแปลงข้อมูลหยุดเมื่อกำกวม ทดสอบซ้ำได้ และไม่มี fallback ไปใช้แหล่งเก่าเงียบ ๆ
- จำนวน รหัส และความสัมพันธ์ของข้อมูลปัจจุบันที่เลือกคงครบ รวมคะแนน/เช็คชื่อที่เดิมอ้างฉบับเก่า
- หลัง cutover ไม่เหลือแถวฉบับเก่า ผู้อ่านเดิม ประวัติแฝง หรือการอ้างอิงค้าง และงานค้างไม่สร้างสิ่งเหล่านี้กลับมา

checkpoint เอกสารใช้การตรวจเอกสารและลิงก์ งานพัฒนาใช้ชุดตรวจตามผลกระทบจริงและการซ้อม migration แยกจาก production
คำสั่งและสูตรทดสอบให้ใช้อ้างอิงจาก [Testing](../../TESTING.md) ไม่ทำสำเนาคำสั่งไว้ในแผนนี้
