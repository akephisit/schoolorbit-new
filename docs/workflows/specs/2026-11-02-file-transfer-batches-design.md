# Staff file-transfer batches

Approved scope: the user requested faster browser transfer, several files and several recipients, and explicitly stopped performance measurement. Functional verification remains required. Existing School staff authentication, tenant/session/device binding, RAM signaling and host-only WebRTC remain authoritative. No service, relay, TURN/STUN provider, native client, database state or new permissions are introduced.

A sender selects one ordered batch and several online recipients. Each recipient sees all file names and sizes and accepts that exact batch once. Files travel sequentially over that recipient's WebRTC connection. At most three recipient pairs run concurrently; the frontend queues the rest without creating server pairs or starting pending expiry. Progress, decline, completion and cancellation are per recipient. Shared identity or signaling loss closes every pair on that device.

Protocol version 2 is explicit. Registration accepts an optional `protocolVersion` field solely so missing or unsupported versions receive a readable refresh-both-devices error; only version 2 creates a device. Snapshots contain `protocolVersion` and named `FileTransferLimits`: three outgoing transfers, twenty files, 64 MiB per file, 128 MiB aggregate batch. Existing pair DTOs replace `file` with ordered `files` and add `clientRequestId`; pair creation supplies both. No endpoint changes are needed. Request IDs correlate HTTP, SSE and reconciliation, never authorize a caller or provide an idempotency receipt. Duplicate active request IDs for one initiating device conflict. Clients never automatically retry an uncertain mutation and reconcile existing pairs instead. There is no v1 bridge or closed-pair resurrection.

The existing Staff runtime validates the complete batch with checked aggregate arithmetic before admission. Pending and accepted pairs both reserve capacity under its single mutex. A sender has no incoming pair and fewer than three outgoing pairs; a recipient has no pair in either role. Every pair retains its own recipient, immutable ordered metadata, explicit consent, signaling direction and expiry. The frontend owns the user-selected batch and recipient queue; the backend owns only accepted runtime state.

Control queues remain bounded at sixteen events per device so three pending/accepted/answer bursts fit without requiring an immediate drain. Presence invalidation remains coalesced separately. Queue overflow, stream drop and session invalidation remove the binding and all associated pairs. Closing one pair releases only its slot. Device limits remain 256 globally, 64 per tenant and three per session; role exclusivity bounds live pairs to 192 globally. File bytes stay entirely in browser data channels. The receiving browser can retain at most one bounded batch; no disk/OPFS workflow is added.

Backend owns Rust DTOs, runtime admission, typed HTTP validation, generated-contract registration, canonical deployed smoke consumers and Operations. Frontend owns the batch transfer state machine, queue, consent/progress UI, throughput implementation and Testing documentation. The Coordinator owns Git and generated artifacts. Existing single-process deployment and authenticated smoke routes remain unchanged; smoke registration supplies protocol 2 and validates its limits.

Compatibility requires both devices to refresh when a new protocol is needed. Fresh v1 registrations fail closed with Thai guidance. Previously running browser transfers retain no persisted server work across an application restart. New clients refuse incompatible snapshots instead of guessing a v1 payload.

Acceptance covers ordered batch bounds including zero-byte files; independent three-recipient consent and signaling; fourth-recipient admission refusal and slot release; correlation conflicts; tenant/session/role denial; ordinary lifecycle bursts and overflow cleanup; real browser multi-file/multi-recipient functional transfer; and canonical registration/SSE smoke. No quantitative benchmark or speed claim is required or authorized.
