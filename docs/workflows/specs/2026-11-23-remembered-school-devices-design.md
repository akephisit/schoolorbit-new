# Remembered School devices

Approved scope, recorded 2026-11-23: keep finite authenticated sessions, add explicit remembered-device restoration, retain Push for a recognized opted-in device, and expose revocation through the existing account-security surface. School owns this change; Admin authentication and notification presentation policy remain outside it.

## Ownership and contracts

`school-auth` owns remembered-device credentials, session creation, restoration, revocation and account/password lifecycle. `school-auth-http` owns exact tenant Origin checks and backend-host cookies. `school-notifications` owns Push registration, version/token fencing, admission, cleanup and delivery. Migration 167 supplies their shared eligibility view without a new domain dependency. The frontend Auth owner coordinates bootstrap/session recovery; arbitrary failed business mutations are never replayed.

1. **Remember the device only after password consent.** Successful password login with `rememberMe=true` creates an opaque 256-bit device credential and an Auth grant. Only digests and coarse device metadata are persisted. Its separate `__Host-schoolorbit_device` cookie is Secure, HttpOnly, SameSite=Lax, Path=/, has no Domain and has a rolling 400-day Max-Age. The grant has no server idle or absolute expiry. New ordinary sessions keep 2-hour idle/12-hour absolute deadlines; opted-in and restored sessions keep 7-day idle/30-day absolute deadlines. Historical `remember_me` sessions stay finite and are never backfilled into grants. Every successful explicit login retires the previous presented browser grant and its child sessions, preventing the previous identity from restoring or receiving future Push.
2. **Restore deliberately and safely.** `POST /api/auth/restore` requires the resolved tenant's exact accepted Origin and a deliberate empty JSON object, rejects unknown fields, and returns the existing `ApiResponse<LoginData>`, session/device cookies and session-bound CSRF header. A live incoming session takes precedence with 409 `session_changed` and no cookies. Absent, malformed, revoked or inactive credentials return 401; store failure returns 503. Rejection never expires a browser cookie. `/me`, ordinary HTTP and realtime validation never restore a device or extend session idle. Under user then grant then session/token locks, acknowledged, domain-separated HMAC rotation stages one pending device digest and deterministic child credential. Concurrent current-credential restores and lost-response retries reproduce the same pair while accepted. Pending-device acknowledgment retires the old credential; an expired/deleted issuance generation can be replaced. Persist only hashes, generation timestamp and child ID; use canonical PostgreSQL microseconds and verify reproduced hashes.
3. **Bind durable Push to the grant.** Add nullable same-user device FKs to sessions and subscriptions. A durable subscription has `remembered_device_id` set and `session_id=expires_at=NULL`; ordinary subscriptions keep their existing session FK and finite expiry. `notification_eligible_push_subscriptions` projects `p.*` through exclusive owner branches plus active account status. A device binding cannot fall back to a session after device revocation. Only a proven, currently active device request may promote a browser registration; no bulk grant/Push backfill. Presentation deadlines and irreversible consume-before-send semantics remain unchanged. Revocation blocks future preparation; already prepared/provider-accepted Push cannot be recalled.
4. **Manage the whole remembered device.** `/auth/sessions` returns ordinary/legacy finite sessions and one stable row per active grant, including dormant devices. A device row uses its grant ID, `rememberMe=true`, nullable `idleExpiresAt`/`absoluteExpiresAt`, and is current when the caller's active session belongs to that grant. Child sessions do not duplicate device rows. Existing selected-device deletion, current logout (including absent/expired session with exact Origin), and logout-all atomically revoke grants with their linked sessions, invalidate identity cache and publish actual child-session revocation events. Account deactivation atomically revokes all grants/children and reactivation never resurrects them. Password change verifies the old password, preserves the current finite-session semantics, rotates the current recognized grant to a fresh credential while retaining its ID/Push, and revokes every other grant/session. The current grant's old/pending credentials are immediately invalid.

## Migration and acceptance

Migration 167 is additive and does not rewrite historical session or subscription values. It enforces same-user grant links and durable subscription shape and adds a user-status trigger for all account-deactivation writers. Runtime grants continue through the canonical migrator. Once durable subscriptions are written, pre-167 consumer binaries are prohibited because their cleanup would delete grant-owned rows. Deploy under universal maintenance and recover forward; canonical operational instructions live in `docs/OPERATIONS.md`.

Acceptance covers ordinary/legacy deadlines, opt-in only, elapsed 7/30/90+ day restore and Push with expired/deleted children, concurrent/lost responses, live-session precedence, stale rejection without Set-Cookie, tenant/origin/cookie parsing, digest collision/refusal, dormant management, all revocation paths, password/current-device retention, deactivation/reactivation, warm cache/realtime invalidation, existing Push fencing and message expiry. Use disposable databases/accounts; no production data mutations are required for acceptance.
