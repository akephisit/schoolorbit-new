# Supply catalog approved design

User approved the catalog design in chat and authorized implementation on 2026-10-14.

Scope: School staff supply catalog in the budget workspace. Categorized items have a standardized name, description, purchase unit, one current private product image and price/shop versions. Catalogue consumers always resolve the latest version. Editing a version changes that version; appending a new version preserves earlier price/shop rows. Images are never historical: replace the shared item image and durably retire the former file. Project writing, VAT, price reminders and permanent source evidence are outside scope.

Personal favorites and personal/shared quantity bundles resolve latest prices. Staff may propose an item with an optional source URL/image. Procurement reviewers can edit every product field before approval. Approval atomically creates an item or appends to an existing item, clears source URL/file relationships and durably deletes source objects. Source and product image purposes are distinct. Rejected proposals also discard temporary sources and unused product images.

Backend ownership: an initial application-owned `modules/supply_catalog` capability with thin session-context handlers, typed DTOs, reusable policy and transactional services. Evaluated a domain crate: compile-invalidation gain is unmeasured for this first capability, while root-owned file adapters are needed; keep a cohesive application module rather than introducing an unsubstantiated crate boundary. No existing domain or schema is replaced. A new additive tenant migration preserves previous schemas and binary compatibility; no destructive cutover is needed.

Contracts: generated School OpenAPI/TypeScript and permission registry. New supply_catalog read.school/manage.school/request.own/approve.school permissions. Existing tenant/session/CSRF middleware and ApiResponse envelope remain owners. Exact procurement unit grants never inherit from budget parent. UUIDv7 IDs, integer satang persistence and decimal-string prices. Bounded paging, normalized name+unit uniqueness, similarity results and stale revision checks. Own resources are server-owned.

Files: canonical File Platform private supply_catalog_image/supply_proposal_source purposes. Validate/lock ready clean stored unexpired owned uploads before attachment and promote retention. Attached file deletion is forbidden through generic delete. Replacement and approval use File Platform transaction deletion and post-commit cleanup, retaining provider retry work. Source links are only validated/rendered, never fetched server-side. Upload normalization is bounded and strips image metadata, with browser HEIC/HEIF and AVIF conversion followed by authoritative server raster resize/compression; standard raster and TIFF/GIF/BMP inputs are decoded server-side. Keep only normalized image objects.

Frontend ownership: loader-owned independent items/categories reads, generated DTO API wrapper, PageShell and canonical UI/app-state components. Lazy action-only proposal/detail/bundle workflows with exact permissions, local mutation patching and disposal of async image/read work. Preserve drafts after failures. No automated retry of ambiguous create/approve requests.

Verification: focused version/duplicate/latest-price/bundle/proposal/file access and race tests, synthetic browser workflows in mobile/desktop and both themes, generated contracts/permissions, git diff checks and scripts/pipeline verify --scope auto. Real private-storage/scanner acceptance requires an isolated configured tenant and is distinct from fixtures.
