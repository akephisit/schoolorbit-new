# Central notification dispatch

## Decision and scope

The user approved central notification ownership while fixing Attendance history contention and notification throughput. `school-notifications` will own one durable dispatch queue, inbox materialization, leases, retry, transport and the tenant worker. Attendance owns its recipient selection, message/template rules, business deduplication and term/student identity ledger. Calendar keeps its business mutations and existing post-commit notification boundary. There is no inbox retention change, transient notification redesign, frontend/API/permission change, pool-budget increase or unrelated schema change.

This design supersedes the Attendance-owned dispatch portion of draft PR120. Keep its history change: `history` uses `begin_report_snapshot` with repeatable-read/read-only isolation, shared module/academic-transition/term guards, and authorization plus virtual/persisted rows on the same connection. Opening history does not finalize or write facts. Do not optimize projection scope without subsequent measurements.

Design input: branch `codex/attendance-lock-notification-queue`, commit `be9522a70cf4111d8c9b6c4e092237a79c26ef2d`, tree `5133c67698e5095fd133a6da99432ec0747272a5`. Status: Senior approved; independent Review pending. This is not evidence of implementation or production capacity.

## Current owners and consumers

- Central `publisher.rs` stores an inbox row and starts a detached Web Push task; `deliver_stored` publishes SSE and invokes push. Push endpoint errors currently log sensitive endpoint/error details and are swallowed after the loop.
- Attendance `services/notifications.rs` owns its queue payload and claim/store/ack operations; its runtime owns delivery. Reset resolves owned inbox IDs; purge waits for materialization but allows stored, unpublished delivery to continue.
- Calendar event delivery, Calendar request workflow and the central create endpoint call `NotificationService::send`. Calendar request/decision mutations commit before notification lookup/storage. This existing gap remains; this change does not make Calendar business mutations transactional with notifications.

Merely moving the concurrent executor would leave durable queue ownership split and preserve central fire-and-forget dispatch. Replace those transport paths with one central worker instead.

## Typed provider contract

The following are internal Rust provider contracts, not new HTTP contracts. Use existing `NotificationType`, `AppError`, UUID and SQLx types; do not add a generic JSON envelope, SQL callback string or reverse dependency on Attendance.

```rust
enum NotificationSource {
    Direct,
    Attendance { source_id: Uuid }, // exact thin-ledger row ID
}
struct QueuedNotification {
    id: Uuid,                     // stable queue ID
    notification_id: Uuid,        // stable existing/new inbox ID
    recipient_id: Uuid,
    source: NotificationSource,
    dedup_key: Option<String>,    // domain-supplied, never regenerated by worker
    title: String,
    message: String,
    type_: NotificationType,
    link: Option<String>,
}
struct ClaimedNotification {
    notification: QueuedNotification,
    lease_token: Uuid,
}
struct NotificationProgress {
    notification_id: Uuid,
    stored_at: Option<DateTime<Utc>>,
    published_at: Option<DateTime<Utc>>,
}
struct EnqueueOutcome {
    input_id: Uuid,                // correlate the caller's candidate
    queue_id: Uuid,                // canonical accepted/existing identity
    notification_id: Uuid,
    source: NotificationSource,    // canonical ledger identity for first-wins replay
    inserted: bool,
}
```

Source storage is exactly `direct` or `attendance`; `source_id` is null only for `direct`. Unsupported stored discriminants produce `notification_source_unsupported`, leave the row undelivered and do not fall back to direct delivery. Attendance source IDs are domain metadata; central code neither queries Attendance tables nor infers academic ownership.

Provider functions are:

```rust
async fn enqueue_in_transaction(
    tx: &mut Transaction<'_, Postgres>, items: &[QueuedNotification],
) -> Result<Vec<EnqueueOutcome>, AppError>;
async fn store_and_enqueue_in_transaction(
    tx: &mut Transaction<'_, Postgres>, item: &QueuedNotification,
) -> Result<Uuid, AppError>;
async fn progress_on_connection(
    connection: &mut PgConnection, notification_ids: &[Uuid],
) -> Result<Vec<NotificationProgress>, AppError>;
async fn cancel_identified_in_transaction(
    tx: &mut Transaction<'_, Postgres>, source: NotificationSourceKind,
    notification_ids: &[Uuid], remove_inbox: bool,
) -> Result<(), AppError>;
```

`NotificationSourceKind` has only `Direct` and `Attendance`. Cancellation callers must establish domain ownership before supplying IDs; the provider additionally filters by the supplied source kind. Missing progress for a live ledger identity is a typed integrity error, never interpreted as delivered. Bulk enqueue returns canonical identities correlated to each input. Attendance preserves its stable student/day advisory guards (namespace1711), inserts its ledger with `ON CONFLICT(recipient_id,dedup_key) DO NOTHING`, and enqueues **only newly inserted ledger rows**, in the same transaction. A second arrival may show a different time but retains the first ledger/message without re-enqueueing changed content. Central replay of an identical stable identity is idempotent; reusing a stable queue/notification ID with a different recipient, source or payload is an integrity error. A provider business-dedup replay returns the original canonical identity rather than overwriting first-accepted content. Never generate replacement IDs. Verify canonical returned identities agree with new ledger entries; conflicts roll back both. Use bulk statements without per-recipient transaction loops.

`NotificationService::send` retains its existing public signature and returned ID. Internally it opens one transaction, stores the inbox row and a dispatch job with `stored_at` set, commits, then wakes the central worker. Immediate inbox visibility remains for Calendar and manual creation. It performs no inline transport or detached per-message push task. Failure after a successful enqueue is not reported as a failed business mutation.

Attendance uses deferred `enqueue_in_transaction`: result save/finalization or digest transaction inserts the domain ledger and central queue atomically; no inbox, SSE or push occurs before commit. The central worker materializes the inbox later, preserving current Attendance semantics. Enqueue itself persists only and does not wake before commit. Its caller wakes centrally after commit; `send` owns its commit and wake internally. A wake is only a hint; periodic discovery recovers a committed enqueue whose caller was interrupted before waking.

## Eligibility and lock order

Central defines an object-safe asynchronous `DeliveryEligibilityPort: Send + Sync`:

```rust
async fn authorize_on_connection(
    &self, connection: &mut PgConnection,
    source: &NotificationSource, recipient_id: Uuid,
) -> Result<bool, AppError>;
```

The root application adapter composes source providers. Attendance implements its part using the exact ledger source ID/recipient, current student-or-guardian relationship and its shared module guard. Direct has no extra domain policy. Central independently checks that the recipient is active. Unknown policy/source errors fail closed; transient lookup errors keep the lease for retry. A definite missing/cancelled source or ineligible recipient is terminal suppression: lock/recheck the existing claimed row and token before setting `published_at`, without inventing `stored_at` or an inbox row. If cancellation already removed the job, complete harmlessly without creating any state. A stale token cannot suppress a newer claim.

For each item, begin a transaction and call the source eligibility port **before** locking its central queue row. The Attendance implementation acquires moduleSHARED before reading its source. Then central locks/reloads the row, checks the supplied lease token and unexpired lease, validates active recipient and materializes the inbox with its stable ID only when `stored_at` is null. If `stored_at` is nonnull but the inbox is absent, never recreate it: suppress further dispatch with a bounded `notification_inbox_missing` finding. Commit before transport. The queue payload is authoritative; reject identity drift instead of silently replacing a different existing inbox. Preserve existing inbox `read_at` and `created_at` on replay. Renew neither the lease nor the stable ID implicitly.

The lock order is domain guard (Attendance module/required domain guards) → central queue rows in queue-ID order → inbox rows. Claim transactions lock only due queue rows and commit before calling any domain policy. They must not hold queue locks while acquiring module guards.

Reset already holds Attendance moduleEXCLUSIVE. It resolves owned ledger identities, calls central cancellation, then deletes domain rows in the same transaction. Cancellation locks matching queue rows in stable order, deletes matching inbox rows, and removes matching dispatch jobs before source deletion. A prefetched item must recheck the locked queue row; after cancellation it cannot recreate an inbox. Never delete central audit history or another source's rows. External delivery already in flight cannot be retracted; do not claim reset retracts an already emitted SSE/push.

Purge retains its existing distinction: block when a nonsuppressed job has not been materialized; allow stored/unpublished dispatch to finish. Query central progress through the provider. Remove only the domain's completed ledger rows as today. A valid pending job whose ledger remains is still eligible after the term archive; do not require an unarchived term in dispatch eligibility.

## Canonical schema and cutover

Migration119 creates an empty `notification_dispatch_jobs` table and indexes. Migration120 performs copy, reconciliation and Attendance contraction in one transaction. Neither edits applied migrations101–118.

| Central column | SQL contract / mapping |
| --- | --- |
| `id` | UUID primary key; copy Attendance `id` |
| `notification_id` | UUID not null unique; copy unchanged |
| `recipient_id` | UUID not null, users FK on delete cascade |
| `source_kind`, `source_id` | checked text `direct`/`attendance`, UUID; shape check above; unique source kind/source ID for nonnull IDs |
| `dedup_key` | nullable text; unique `(source_kind, recipient_id, dedup_key)`; Attendance keys unchanged, direct sends may omit |
| `title`, `message`, `link` | text, text, nullable text; copy payload exactly, without truncation |
| `type` | text checked to existing info/success/warning/error values; Attendance maps to info |
| `created_at` | timestamptz not null; copy original queue creation time |
| `stored_at`, `published_at` | nullable timestamptz; copy exactly |
| `next_attempt_at` | timestamptz not null; copy including future leases |
| `attempts` | integer not null, nonnegative; copy exactly |
| `lease_token` | nullable UUID; null for migrated rows, replaced on a fresh due claim |

Use the partial due index `(next_attempt_at, id) WHERE published_at IS NULL`. No academic table FK or generic JSON metadata belongs to this table.

Attendance keeps `id`, `academic_term_id`, `recipient_id`, `student_id`, `dedup_key`, `notification_id`, `created_at` and its existing recipient/dedup constraint. It drops payload and transport columns only after reconciliation. This thin ledger supplies domain ownership, reset impact identity and guardian policy; it is not a second queue. Central progress supplies transport state to purge and tests.

Migration120 maps every legacy row, including published-with-null-stored suppression, stored/unpublished rows and future retry leases. Migration107 changed queue ID defaults to UUIDv7, not `notification_id`; preserve the original UUID version and value of both. Do not materialize absent inboxes during migration. Preserve existing inbox rows byte-for-byte, including read timestamps, even when an absent inbox was intentionally suppressed. Reject duplicate notification IDs, negative attempts, titles exceeding the existing inbox255-character width, unexpected preexisting queue mappings, recipient/payload collisions with existing inbox IDs, invalid source shapes or unrepresentable state with bounded codes such as `NOTIFICATION_DISPATCH_IDENTITY_CONFLICT`, `NOTIFICATION_DISPATCH_PAYLOAD_UNMAPPABLE`, `NOTIFICATION_DISPATCH_INBOX_CONFLICT` and `NOTIFICATION_DISPATCH_PRESERVATION_FAILED`. Never normalize negative attempts or truncate text. Compare counts, complete stable identity sets, dedup, payload and every timestamp/attempt before dropping columns. Test rollback/refusal and retry of120 against119; never repair by replacing UUIDs or deleting source/audit rows.

119 is structurally additive, **not operational permission to run the old binary**. `school_migrations::verify_tenant_schema` requires the compiled migration count/checksums to equal applied history; the118 binary cannot start/reacquire after119. Keep that gate unchanged. After120 the old code also references removed columns. Once history advances, recovery requires a matching-timeline forward build under maintenance; no rollback to an118 binary.

## Worker, leases and transport

Start one central worker from the root application. Remove Attendance claim/store/transport polling, pending state and dispatch wake management; retain its schedule/digest/finalization/Behavior work and invoke the central post-commit wake for produced notifications. Calendar reminder scheduling remains domain work; its output uses central send.

The worker registry caches only tenant names and pending/scheduling bits, never copied database URLs or school-status snapshots outside the AdminClient directory TTL/fencing contract, raw `PgPool` clones or retained `TenantPool` leases. Refresh directory discovery periodically (300 seconds), poll retry work every15 seconds, and accept post-commit wake hints. On startup/discovery visit all active tenants so persisted queues survive restarts and lost wake hints. Startup may overlap maintenance/migrations: retain failed discovery/admission candidates for bounded regular-tick retry, never cache them as empty or defer their backlog solely to the300-second refresh. Preserve the schema-history gate; do not repair schema or run DDL from the worker. Reacquire a proper `TenantPool` for each logical pass and retain it through all item awaits. Process at most one bounded claim per tenant per pass. Revisit all candidates before another due-work pass; a tenant admission/directory/database failure must defer that tenant and continue the others. Bound per-tenant directory/admission attempts to5 seconds using cancellation-safe existing clients/pool reservations. Retry failed directory refresh on the regular tick without discarding already-known tenants.

Claim at most32 due rows with `FOR UPDATE SKIP LOCKED`; invalid active-recipient pruning consumes the same bounded claim. Allocate a fresh lease token, increment attempts and set `next_attempt_at=now()+120 seconds`. An existing future lease is not due. All materialize/ack/suppress operations fence by queue ID plus lease token; stale work cannot acknowledge or overwrite a newer lease. Crash recovery waits until the durable due time.

Use four unspawned in-flight item futures, five seconds for the whole item (eligibility, materialization, transport and acknowledgement), and await every sibling outcome independently. The parent tenant lease remains alive until every future completes or is dropped on cancellation. No `try_join` cancellation of claimed siblings and no detached raw pool clones.32/4×5 gives40 seconds of item work, leaving margin below the120-second lease; bound claim/status database work as well. Wake immediately only if due rows remain, after finishing the tenant pass. Future leased retries alone must not create a wake loop.

Transport uses existing tenant/user SSE events and stable notification IDs. No SSE receiver is a successful best-effort publication. No subscriptions means successful dispatch without requiring VAPID. Attempt all subscriptions unless the whole-item deadline expires. Remove invalid/not-found subscriptions as terminal endpoints; aggregate and propagate retryable endpoint/configuration/database failures after attempting siblings, leaving the job leased for retry. Replace raw endpoint and Debug-error logging at this affected boundary with safe aggregate codes/counts and internal UUIDs. Successful devices may receive a repeated stable ID when another endpoint fails; delivery remains at least once. No exactly-once ordering, browser receipt or Web Push receipt guarantee is added.
