# แบบฟอร์มบุคลากรที่ง่ายขึ้นและรายการตำแหน่งมาตรฐาน

วันที่: 2026-10-03 · ฐานที่ตรวจ: `527e7a26` · สาขา: `codex/personnel-data-simplification`

## เป้าหมายและขอบเขตที่ตกลง

ผู้ใช้ต้องการเลิกจัดการรายการกลางสำหรับตำแหน่ง สาขา และสถาบันด้วยตนเอง ตำแหน่ง วิทยฐานะ และระดับวุฒิยังต้องเลือกจากค่ามาตรฐานเพื่อกรองและสรุป Dashboard ได้ ส่วนสาขาและสถาบันให้พิมพ์เอง โดยรักษาข้อมูลบุคลากรเดิมครบถ้วน

แนวทางรวมที่ผู้ใช้ตอบรับแบ่งเป็นสามงานซึ่งส่งมอบและตรวจสอบแยกกัน:

1. **งานใน specification นี้:** ปรับแบบฟอร์ม ย้ายสาขา/สถาบันเป็นข้อความของบุคลากร และยกเลิกระบบจัดการรายการกลาง ใช้รายการตำแหน่งที่ระบบดูแล
2. **งานถัดไป:** เพิ่มประเภทบุคลากรและประวัติตำแหน่ง/วิทยฐานะที่มีวันที่และคำสั่งอ้างอิง
3. **งานถัดจากประวัติ:** เพิ่มเกณฑ์ที่ระบุเวอร์ชัน คำนวณวันครบระยะเวลาและสถานะตรวจคุณสมบัติ แล้วนำเสนอในโปรไฟล์และ Dashboard

งานที่สองและสามต้องมี specification และ implementation plan ของตนเองก่อนลงโค้ด เก็บข้อมูลพื้นฐานได้ทุกประเภทบุคลากร แต่การคำนวณระยะแรกมุ่งข้าราชการครูสายการสอนตามเกณฑ์ ก.ค.ศ. การคำนวณสายบริหารหรือความก้าวหน้าบุคลากรประเภทอื่นเป็นการขยายภายหลัง

ความสำเร็จของงานแรก: ผู้ใช้สร้างและแก้ไขบุคลากรโดยไม่ต้องเปิดหน้ารายการกลาง กรอกสาขา/สถาบันได้โดยตรง ตำแหน่ง/วิทยฐานะ/วุฒิยังกรองได้ และข้อมูลเดิมไม่ถูกเดาหรือสูญหาย

## สิ่งที่ตรวจจากระบบปัจจุบัน

- Migration `081_staff_personnel_data.sql` สร้าง `staff_reference_items` รวมสามชนิด และแทนข้อความสาขา/สถาบันด้วย foreign key; migration ล่าสุดในฐานที่ตรวจคือ `082_staff_retirement_status.sql`
- วิทยฐานะและวุฒิเป็น enum อยู่แล้วใน `backend-school/crates/school-staff/src/personnel.rs` ไม่ใช่รายการที่ผู้ใช้เพิ่มเอง
- ตำแหน่งใช้ UUID และ stable code ของรายการกลาง ทั้ง profile, directory, filter URL และ Dashboard ใช้ความสัมพันธ์นี้
- แบบฟอร์มร่วม `StaffPersonnelFields.svelte` ใช้ตัวเลือกค้นหารายการกลางทั้งสามช่อง มีลิงก์ไปหน้าจัดการ และถูกใช้ในกระบวนการสร้าง/แก้ไขบุคลากร
- Backend มี `GET/POST /api/staff/reference-items` และ `PATCH /api/staff/reference-items/{id}`; การเขียนใช้ `STAFF_UPDATE_ALL` และการอ่านรองรับผู้อ่าน profile หรือผู้สร้าง/แก้ไขบุคลากร
- กลุ่มสาระคำนวณจากสังกัดปัจจุบันอยู่แล้ว ส่วนประเภทการจ้างเดิมไม่เพียงพอที่จะยืนยันสถานะข้าราชการสำหรับการคำนวณวิทยฐานะ

รายละเอียดของโค้ด สัญญา API และ schema เป็นแหล่งจริง; ข้อความนี้กำหนดการเปลี่ยนแปลง ไม่แทนที่เจ้าของเหล่านั้น

## ทางเลือกและการตัดสินใจ

ใช้ **รายการตำแหน่งมาตรฐานที่ระบบดูแลในฐานข้อมูล** แยกเป็น `staff_job_positions` และรักษา UUID เดิม แทนการเปลี่ยนตำแหน่งทั้งหมดเป็น enum ในการย้ายครั้งนี้ วิธีนี้เก็บความหมายของตำแหน่งที่อาจเคยเพิ่มหรือแก้ชื่อไว้ และรักษา deep link ของตัวกรองได้ โดยไม่เปิดให้ผู้ใช้สร้างหรือแก้รายการอีก

การใช้ enum ของตำแหน่งทั้งหมดต้องแปลงรายการที่เคยเพิ่มเองให้ตรงค่าปิด ซึ่งอาจเดาความหมายผิด ส่วนการคงหน้าจัดการ generic catalog ทำให้แบบฟอร์มยังต้องพึ่งกระบวนการที่ผู้ใช้ต้องการยกเลิก จึงไม่เลือกสองแนวทางนี้

รายการตำแหน่งมาตรฐานไม่ใช่เกณฑ์การเลื่อนวิทยฐานะ การคำนวณในงานถัดไปต้องใช้ประเภทบุคลากร ประวัติ วันที่ และกติกาที่ใช้บังคับ ไม่ตัดสินจากชื่อที่แสดงหรือบทบาทสิทธิ์ในระบบ

## โครงข้อมูลหลังเปลี่ยน

### ตำแหน่ง

`staff_job_positions` เป็น canonical owner ของตำแหน่ง มี UUID, code, ชื่อ, สถานะ active, ลำดับ, เวลาเดิม และสถานะเลือกสำหรับการกำหนดใหม่ ไม่มี API เขียนรายการโดยผู้ใช้ การปรับรายการของระบบทำผ่าน release และ migration ที่ตรวจแล้ว

ค่ามาตรฐานสำหรับการเลือกใหม่ใช้เจ็ด code เดิม: `teacher`, `assistant_teacher`, `contract_teacher`, `government_employee_teacher`, `school_director`, `deputy_school_director`, `support_staff` รายการต้อง active ด้วย ชื่อเดิมที่บันทึกใน catalog ถูกเก็บตามจริง ไม่เขียนทับตามการคาดเดา

ย้ายรายการชนิดตำแหน่งทุกแถวพร้อม UUID/code/ชื่อ/สถานะ/ลำดับ/เวลา แม้เป็นรายการนอกชุดมาตรฐาน รายการนอกชุดไม่ให้เลือกกำหนดใหม่ แต่ผู้ที่มีรายการนั้นอยู่ยังเห็นชื่อเดิม เก็บค่าเดิมเมื่อแก้ช่องอื่น กรองและคลิกจากกราฟได้ และเปลี่ยนไปตำแหน่งมาตรฐานหรือล้างค่าได้ตามสิทธิ์ ห้ามเดารายการเหล่านี้เป็นครูหรืออนุมานสถานะข้าราชการ

`staff_info.job_position_id` ชี้ table ใหม่ด้วย foreign key UUID เดิม การส่งค่าเดิมที่ไม่ได้เปิดให้เลือกใหม่ยอมรับเฉพาะบุคลากรที่ถือค่านั้นอยู่ Backend ต้องปฏิเสธการกำหนดค่าดังกล่าวให้คนใหม่ รวมถึง ID ที่ไม่มีจริง การแก้ไขตำแหน่งยังอยู่ใน transaction ของเจ้าของข้อมูลบุคลากร

### สาขาและสถาบัน

เพิ่มข้อความ nullable `staff_info.major` และ `staff_info.university` ความยาวสูงสุด 200 Unicode scalar values ต่อช่อง เมื่อรับข้อมูลใหม่ให้ตัด whitespace รอบข้อความ รักษาตัวสะกดและช่องว่างภายใน ปฏิเสธ control characters และค่าที่ยาวเกินขอบเขต ช่องว่างล้วนเท่ากับล้างข้อมูล ไม่รวมชื่อคล้ายกันอัตโนมัติ

ย้ายชื่อที่ join จากรายการเดิมมาเก็บกับเจ้าของข้อมูลแต่ละคน รวมรายการที่ปิดใช้งานอยู่แล้ว รักษา null ตามจริง และไม่อนุมานข้อความจาก ID ที่สัมพันธ์ไม่ถูกต้อง การส่ง patch ที่ไม่ระบุช่องคงค่าเดิม ส่วน explicit null ล้างช่องได้

หลังสลับระบบแล้ว major/university ไม่มี table รายการกลางเป็น runtime owner อีก ไม่สร้าง catalog หรือ autocomplete จากข้อมูลบุคลากรทั้งโรงเรียนในงานนี้ ชื่อที่ไม่เคยผูกกับบุคลากรเป็นตัวเลือกของหน้าที่เลิกใช้ ไม่ใช่ข้อมูลการศึกษาของบุคลากร; การลบตัวเลือกเหล่านี้ต้องอยู่ใน inventory และ gate ของการยกเลิก catalog

### ข้อมูลที่คงพฤติกรรมเดิม

วิทยฐานะและระดับวุฒิคง enum, label และความต่างระหว่างยังไม่ระบุ/ไม่มีวิทยฐานะ/ไม่ใช้กับตำแหน่งนี้ กลุ่มสาระยังมาจากสังกัดปัจจุบัน ใบอนุญาต การจ้าง metadata อัตลักษณ์บุคลากร สถานะบัญชี และสังกัดไม่ถูกเปลี่ยนจากการย้ายนี้

## API และสิทธิ์

- เพิ่ม `GET /api/staff/job-positions` สำหรับรายการตำแหน่งแบบอ่านอย่างเดียว รองรับค้นหาและ pagination ที่มีขอบเขต และ DTO ที่บอกว่าเลือกกำหนดใหม่ได้หรือไม่ หน้า filter ต้องดูตำแหน่งที่มีผู้ถืออยู่ได้ด้วย; แบบฟอร์มเลือกใหม่ใช้รายการที่พร้อมเลือกเท่านั้น
- คง `job_position_id` และ URL filter เดิม เพื่อรักษา identity และ deep link ใช้ summary ของตำแหน่งที่มีชื่อชนิดชัดเจนแทน generic reference DTO
- Create/update staff info รับ `major` และ `university` เป็นข้อความ nullable Response ส่งสองช่องนี้เป็นข้อความ nullable สอดคล้องกันทั้ง OpenAPI และ generated TypeScript ลบ `major_id`/`university_id` ออกจาก wire contract หลัง cutover
- ลบ route registration, handler, OpenAPI paths/schemas, API wrapper และ service ของ generic reference CRUD หลังผู้ใช้ทุกจุดเปลี่ยนมา canonical owner ใหม่ ไม่ทิ้ง endpoint เก่าเป็น alias
- สิทธิ์อ่านรายการตำแหน่งใช้ชุด capability ปัจจุบันของ reference read โดยใช้ generated constants ไม่มีสิทธิ์เขียน catalog ใน endpoint ใหม่ การอ่าน/แก้ profile ของบุคลากรยังผ่าน resource policy ของ workflow เดิม การอ่าน catalog ไม่ให้สิทธิ์อ่าน profile หรือยอดทั้งโรงเรียน
- Dashboard และ directory คง scope union ของ `staff_profile.read.own`, `.organization_unit`, `.organization_tree`, `.school` และต้องนับตรงกันหลังเปลี่ยน join
- ไม่เพิ่ม permission code ใหม่ในงานนี้ ไม่ใช้ realtime ส่งข้อความสาขา/สถาบันหรือข้อมูล profile เพิ่มเติม สัญญาณเปลี่ยนบุคลากรเดิมยังให้ client อ่านผลที่ได้รับอนุญาตจาก HTTP

Business logic และ SQL อยู่ใน `school-staff`; handler จำกัด context/policy/service/response Crate นี้เป็นเจ้าของบุคลากรอยู่แล้ว จึงเพิ่ม module ตามความรับผิดชอบโดยไม่แยก crate ใหม่ซึ่งไม่มีประโยชน์ด้านขอบเขต dependency ที่พิสูจน์ได้สำหรับงานนี้

## ประสบการณ์ใช้งานและสถานะหน้าจอ

หน้าเพิ่มและแก้ไขใช้ฟอร์มร่วม: ตำแหน่งเป็น dropdown ค้นหาได้ วิทยฐานะและวุฒิเป็น dropdown เดิม สาขาและสถาบันเป็น Input มี label ที่สัมพันธ์กับช่องและ validation เฉพาะช่อง แสดงคำแนะนำว่าพิมพ์ตามชื่อวุฒิหรือเอกสารได้ ไม่บังคับลงทะเบียนชื่อก่อนกรอก

หน้าตรวจทานและรายละเอียดแสดงข้อความสาขา/สถาบันตามข้อมูลบุคลากร เมื่อไม่ระบุใช้สถานะข้อมูลว่างเดิม ลบปุ่ม “จัดการรายการกลาง” จาก directory และลิงก์จากแบบฟอร์ม ยกเลิก `/staff/manage/reference-data` และ route metadata ที่เกี่ยวข้อง ลิงก์เก่าถึงหน้าที่ไม่มีอยู่ตามระบบ 404 ไม่ redirect ไปหน้าอื่นพร้อมการกระทำ

ตัวเลือกตำแหน่งเป็น interaction-only read เมื่อเปิดตัวเลือก มี skeleton/error/retry และยกเลิกคำขอที่ถูกแทนที่ ฟอร์มต้องเก็บ draft เมื่อโหลดตัวเลือกหรือบันทึกไม่สำเร็จ ค่าปัจจุบันต้องแสดงจาก resource ที่อ่านได้โดยไม่รอรายการเลือก สาขา/สถาบันไม่มีคำขอโหลด catalog

ใช้ shared Input, Select/Popover, Button, PageShell และ app-state ตาม `.rules` คงคุณภาพ UI ของ directory และ Dashboard ที่เพิ่งปรับ ตรวจมือถือและ desktop ทั้งสอง theme รวม pending, error, empty และ validation

## การย้ายข้อมูลและการกู้คืน

ห้ามแก้ migration 081 หรือ 082 เพิ่ม migration ต่อเนื่องจาก timeline ณ ลงมือจริง โดยผ่าน tenant migration runner เดียวของระบบ

ลำดับที่ต้องพิสูจน์ด้วย gate: expand table/columns → backfill จาก source snapshot ที่ล็อก → reconcile → สลับ consumers → contract/cleanup ทั้งข้อมูลและ binaries รุ่นเก่าต้องไม่เขียนระหว่างช่วงนี้ ใช้ maintenance ของ release flow และตรวจทุก tenant ก่อนเปิดให้เขียนอีก

Reconciliation ต้องตรวจ staff_info identity/count, user relationship, ตำแหน่งทุก UUID/code/name/status/order/time, ชื่อ major/university ต่อบุคลากรแบบ exact comparison รวม null, การรักษาวิทยฐานะ/วุฒิ/การจ้าง/ใบอนุญาต/metadata/created_at และไม่มี FK ผิดชนิดหรือสูญหาย รายงานเฉพาะ bounded finding codes และ aggregate counts ไม่ส่งชื่อจริงหรือ raw rows

ผลตรวจต้องผูกกับ source ที่ใช้และ migration รุ่นใหม่ ห้ามใช้ audit ของ migration 81 แทนหลักฐานการย้ายครั้งนี้ ถ้าหลักฐานหาย เก่า ไม่ครบ หรือมีความสัมพันธ์แปลงไม่ได้ ให้ปฏิเสธทั้ง consumer cutover และ destructive cleanup และใช้ remediation ที่ตรวจแล้วก่อนลองใหม่

ช่วง expand ใช้เพื่อย้ายภายใต้ maintenance เท่านั้น ไม่เพิ่ม runtime dual-write/dual-read หลัง cutover ลบ FK/คอลัมน์ชนิดอ้างอิงของ major/university, generated kind columns ที่ไม่ใช้, generic catalog table/function และ owner เดิมเมื่อหลักฐานครบ ประวัติ audit ที่จำเป็นยังเก็บตาม lifecycle ของระบบ ไม่ทำ archive ของข้อมูลบุคลากรซ้ำ

หลัง schema/API cutover ห้ามนำ binary รุ่นที่ใช้ catalog เก่ากลับมา Recovery ใช้ roll-forward ที่ผ่าน rehearsal หรือกู้ฐานและ application เป็นชุดเดียวจาก protected snapshot ก่อน cutover ตาม Operations ไม่สมมติว่าย้อนเฉพาะ image ได้

## เกณฑ์ตรวจรับและการทดสอบสำหรับ implementation plan

1. Fixture ก่อนย้ายที่มีชื่อไทย รายการปิดใช้งาน null หลายคนใช้ชื่อเดียวกัน และตำแหน่งนอกชุดมาตรฐาน ย้ายได้โดยเก็บความหมาย/identity/ความสัมพันธ์ครบ ไม่เดาตำแหน่ง
2. Missing/wrong-kind FK, source drift และ audit ที่หาย/เก่า/ไม่ครบปิด gate ของ cutover และ cleanup การลองใหม่ไม่สร้างสำเนาหรือทิ้ง state บางส่วน
3. สร้าง/แก้ไข/อ่านข้อมูลใหม่ได้ทั้งข้อความใหม่ คงค่าเดิม ล้างด้วย null และไม่ส่งช่อง; validation ยาวเกิน/control characters ไม่ล้าง draft และไม่กระทบใบอนุญาตหรือช่องอื่น
4. ไม่กำหนดตำแหน่งนอกชุดหรือ inactive ให้คนใหม่ แต่คงตำแหน่งเดิมได้เมื่อแก้ช่องอื่น Directory/aggregate/filter ยังใช้ UUID เดิมและมียอดตรงกันในทุก scope ที่อนุญาต
5. ผู้อ่านอย่างเดียวไม่เรียก API เขียนหรือข้อมูล action-only ผู้ไม่มีสิทธิ์ไม่ได้ทั้ง catalog และ profile ที่เกิน scope ไม่มีเส้นทาง generic CRUD ที่ยังเขียนได้
6. Synthetic Playwright ครอบคลุมสร้าง แก้ รายละเอียด กรอง chart drilldown, stale option response, error/retry, draft preservation และ responsive/theme states โดยไม่เรียก major/university catalog หรือ link หน้ารายการกลาง
7. รัน focused `school-staff`/policy/cutover tests, backend matrix, generated API checks, frontend matrix และ browser workflow ตาม `.rules` และ `docs/TESTING.md` การย้าย provider ใช้ disposable/protected copy และตรวจ release/tenant audit/deployed read-only acceptance ก่อนกล่าวว่าปรับครบ

implementation plan ต้องระบุไฟล์ signatures DTO และคำสั่งที่แน่นอนตามเจ้าของเหล่านี้ เพิ่ม coverage ที่พิสูจน์พฤติกรรมจริง ไม่เพียงแก้ static test ให้ยอมรับข้อความใหม่

## ข้อกำหนดที่ส่งต่อไปงานประวัติและการคำนวณ

งานประวัติต้องแยกประเภทบุคลากรออกจากตำแหน่งและ generic employment_type เก็บวันที่มีผลของตำแหน่ง/วิทยฐานะ แยกวันที่ออกคำสั่งกับวันที่มีผล เก็บประวัติย้อนหลัง และไม่สร้างวันที่จากข้อมูลปัจจุบันที่ไม่เคยบันทึก

งานคำนวณต้องระบุชุดเกณฑ์ เอกสารอ้างอิง ช่วงใช้บังคับ เงื่อนไขลดระยะเวลา และหลักฐานการตรวจ ใช้วันแบบ calendar date และแสดง พ.ศ. ตาม UI ไม่คูณจำนวนปีด้วย 365 ไม่คำนวณให้กลุ่มที่ไม่เข้าข่าย หากข้อมูลหรือกติกายังไม่รองรับให้บอกสถานะอย่างชัดเจน

แยก “วันครบระยะเวลาขั้นต่ำ” จาก “คุณสมบัติครบสำหรับยื่น” วันที่อย่างเดียวไม่ทำให้ผ่านเงื่อนไขอื่น Dashboard เสนอการ์ดและตารางเรียงวันที่สำหรับใกล้ครบ 90 วัน ครบระยะเวลาแต่รอตรวจ และข้อมูลไม่ครบ โดยใช้ขอบเขต profile เดิม ไม่มีการตั้งแจ้งเตือนหรือส่งข้อความภายนอกในงานแรก

หลักฐานที่พบสำหรับเตรียมงานคำนวณ: [หลักเกณฑ์ PA ของ ก.ค.ศ.](https://www.otepc.go.th/en/pa-download/pa-criteria.html), [ล 587/2569 เรื่องเงื่อนไขคุณวุฒิปริญญาโท](https://www.otepc.go.th/en/pa-download/pa-criteria/item/6043-587-2569.html), และ [ว 12/2569 เรื่องพื้นที่พิเศษ](https://www.otepc.go.th/en/pa-download/pa-criteria/item/6022-12-2569.html) รายการนี้ไม่ถือเป็นการตรวจสูตรหรือคุณสมบัติรายบุคคล ต้องอ่านฉบับเต็มและเกณฑ์แก้ไขที่เกี่ยวข้องในการจัดทำ specification ของงานคำนวณ
