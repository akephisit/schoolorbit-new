# Calendar event requests and date-based calendar

The user approved requests that require administrator approval. Requests contain only title, dates, all-day/time, optional location and required description. The requesting user is derived from the authenticated session. Categories, tags, visibility, target audiences and reminders are set by a calendar manager during approval. Neither requests nor events require the academic year or term selected in the application header. New event forms default both dates to the calendar's selected day.

Calendar owns this workflow in the existing school-calendar crate; no new crate is warranted because requests and event creation share validation, persistence and lifecycle. Readers with the new calendar.request.own capability can submit and track their own requests; calendar.manage.school can review all requests, approve using the complete event form or reject with a reason. Approval atomically creates one event and completes the pending request. Pending and rejected requests never enter event reads or reminder delivery.

Calendar events become date-based resources, independent of academic context. Existing event identities, dates, categories, targets, tags, reminders and actors are preserved. Former academic context is recorded in migration provenance before retiring academic event linkage; classroom target selection retains explicit room identity. Calendar audiences and recipient selection must continue to enforce staff/student/parent visibility using enrollment appropriate to the event date. The expansion and migration are verified on disposable data, and runtime cleanup only follows verified preservation. Old binaries cannot be used after academic-column cleanup; recovery rolls forward.

Verification covers request ownership, unauthorized mutations, validation, approval/rejection, atomic rollback, concurrent approval, independent calendar navigation, selected-date defaults, no-year routes and unchanged public/audience boundaries. Run required backend, permission, API, frontend and browser checks before integration. Missing verification dependencies block integration and must be reported.
