# Supervision consecutive-period booking design

Approved scope: one observation contains one or more actual teaching periods on one Bangkok civil date, all for the same exact homeroom UUID. Subjects and physical rooms may differ. Sort by actual bell start and require every end to equal the next start; reject duplicates, overlaps, gaps, lunch breaks, another teacher/context and stale timetable evidence. There is no arbitrary two-period limit.

School Supervision remains the cohesive owner; separate period, booking and deletion modules provide narrower internal responsibilities without creating another crate. Timetable's public dated-teaching snapshot and Delivery's current teacher-assignment provider supply eligibility. No consumer-owned schedule SQL or label inference is introduced.

Canonical storage is ordered supervision_observation_periods. Observations retain identity, academic context, workflow, evaluators and actions. Periods own nullable current allocation/group/homeroom references, exact observed_at, nullable known ends_at, unchanged raw JSON evidence and all historical manual fields/reason. The parent wire observedAt is an earliest-period projection only. New manual/custom inputs and old single-period transport fields are rejected. Historical manual/detached/unknown evidence remains readable and existing planned workflows can finish; returned teacher corrections select a current valid schedule.

Migrations 164 and 165 implement expansion/backfill/reconciliation and gated destructive cleanup. Each legacy observation maps bijectively to one evidence period; preserve timestamps exactly, including values originating from migration 008 requested_at. Do not infer historical ends from today's timetable. Preserve raw JSON unknown keys and every manual value. Verify counts, identities, full evidence, all nonlesson parent fields and descendants before cleanup. Unknown external dependencies, missing/stale evidence and any mismatch refuse atomically. No archive or compatibility endpoint remains. Pre-165 binaries are prohibited after cleanup. Deploy under universal maintenance using canonical all-tenant migration and roll forward on failure.

Weekly booking options and writes use the same Monday-through-Sunday snapshot digest. Create options require own-request permission; observation options use existing resource policy for its teacher/manager. The server resolves exact timestamps and validates current Delivery ownership. Evaluator conflicts compare every canonical interval globally, with existing status exclusions. Historical unknown-end evidence is an exact point: points conflict with equal points or a containing half-open interval. Sorted evaluator/date advisory locks serialize cross-cycle approvals and edits. Existing submitted evaluation immutability and optional-evaluator certification rules remain.

Permanent cycle deletion is a capability only; no production cycle is deleted during implementation. School manage permission gates preview and DELETE. Preview hashes the entire ordered owned graph and returns typed counts; DELETE requires its revision and explicit frontend confirmation. Acquire lifecycle transition, sorted years and all annual child terms, cycle, then observation locks; recheck context before deletion. Reject cross-observation response/evaluator graphs and unknown external dependencies. Atomically delete only the selected cycle, targets, observations, periods, evaluators, responses and actions. Shared templates/staff/academic/timetable resources survive. Missing is 404, denied 403, stale/closed/malformed graph 409.

Verification covers exact-room identity, different subjects, one/two/three periods, gaps/lunch/duplicates/overlap/wrong date/teacher/term/stale sources, later-period conflicts and concurrent approval, atomic correction and submitted immutability, populated raw/manual timestamp migration preservation/refusal/retry, partial source detachment/reporting, full-status and annual deletion graph/hash/concurrency/permission/tenant/shared-data preservation, generated contracts and both Rust feature modes. Durable commands and recovery guidance belong only in TESTING and OPERATIONS. Retire this artifact after the PR records the outcome.
