# ประเภทบุคลากรและประวัติตำแหน่ง/วิทยฐานะ

วันที่: 2026-10-03 · ฐานที่ตรวจ: `300615ae86dc572651101bf39c2a68fd4946702d` · สาขา: `codex/personnel-career-history`

## เป้าหมายและขอบเขต

ต่อจากแบบฟอร์มและ Dashboard ที่ส่งมอบแล้ว ให้ฝ่ายบุคคลบันทึกได้ว่าบุคลากรเป็นประเภทใด ได้รับตำแหน่งและวิทยฐานะเมื่อใด และอ้างอิงคำสั่งใด พร้อมดูประวัติย้อนหลังได้ โดยรักษาข้อมูลเดิมและไม่สร้างวันที่จากการคาดเดา

ยึดการแบ่งงานใน [แบบที่ผู้ใช้อนุมัติไว้](./2026-10-03-personnel-data-simplification-design.md): ส่งมอบประวัติก่อน แล้วจัดทำ specification และ implementation plan ของการคำนวณวันครบระยะเวลาเป็นงานต่อเนื่องแยกกัน งานนี้เตรียมข้อมูลต้นทางให้การคำนวณ แต่ยังไม่แสดงวันยื่นครั้งถัดไปหรือยืนยันสิทธิ์ยื่นจากสูตรที่ยังไม่ได้ตรวจฉบับเต็ม

ความสำเร็จ: บันทึกวันที่มีผลแยกจากวันที่ออกคำสั่ง ดูและแก้ประวัติที่ผิดได้ ข้อมูลปัจจุบันไม่ขัดกับรายการที่อ้างอิง และการแก้ข้อมูลทั่วไปไม่ทำให้ประวัติหรือวันที่หาย หน้าเดิมยังกรองและนับตำแหน่ง/วิทยฐานะได้ตรงกันใน scope ที่อนุญาต

## สิ่งที่ตรวจจากระบบ

- เจ้าของข้อมูลอยู่ใน `backend-school/crates/school-staff` โดย `staff_info_service.rs` เป็นผู้เขียนตำแหน่งและวิทยฐานะใน transaction ของ `staff_service.rs` ที่ล็อกแถวบุคลากร
- `staff_info` มีตำแหน่ง วิทยฐานะ วุฒิ สาขา สถาบัน ใบอนุญาต และประเภทการจ้างเดิม แต่ไม่มีวันที่มีผลหรือประวัติ ประเภทการจ้าง `permanent/contract/temporary/part_time` ไม่ระบุสถานะข้าราชการ
- `users.hired_date` คือวันที่เริ่มงาน ไม่ใช่หลักฐานวันที่แต่งตั้งเป็นครูหรือได้รับวิทยฐานะ
- ตำแหน่งใช้ UUID ของ `staff_job_positions`; วิทยฐานะและวุฒิใช้ enum มีความต่างระหว่าง null, ไม่มีวิทยฐานะ และไม่ใช้กับตำแหน่งนี้
- การอ่าน profile/directory/overview ใช้สิทธิ์ `staff_profile.read` และ resource policy ร่วมกัน การเขียนข้อมูลบุคลากรใช้ `STAFF_CREATE_ALL` / `STAFF_UPDATE_ALL` มี transactional audit helper อยู่ใน crate แล้ว
- หน้าเพิ่ม/แก้ใช้ `StaffPersonnelFields.svelte` ร่วมกัน มี draft ที่ผูกผู้ใช้และ origin พร้อมอายุ 30 นาที หน้ารายละเอียดมี loader ของ profile แยกจากข้อมูลอื่น
- Migration ล่าสุดคือ 084 ไม่มีเหตุให้คืนระบบรายการกลางหรือ personnel migration endpoint ที่เพิ่งถอดออก

## ทางเลือกและข้อเสนอ

เลือก **ประวัติที่มีรายการอ้างอิงของข้อมูลปัจจุบัน และ service เจ้าของเดียวที่เขียนทั้งสองส่วนใน transaction** ใช้คอลัมน์ปัจจุบันเป็น read projection สำหรับ profile/directory/overview เพื่อรักษาเส้นทางค้นหาเดิม ประวัติเป็นเจ้าของวันที่และคำสั่ง ทุกการเปลี่ยนตำแหน่ง วิทยฐานะ หรือประเภทบุคลากรผ่าน service นี้ ไม่มีการเขียน projection อิสระ

การเพิ่มวันที่เฉพาะค่าปัจจุบันง่ายกว่า แต่สูญเสียประวัติเมื่อเปลี่ยนวิทยฐานะและไม่รองรับคำสั่งย้อนหลัง จึงไม่ตอบเป้าหมาย ส่วนการคำนวณค่าปัจจุบันจาก event ทั้งหมดตามวันที่ทุกครั้งเพิ่มปัญหารายการไม่มีวันที่ คำสั่งย้อนหลัง และคำสั่งในอนาคตโดยไม่จำเป็น จึงยังไม่เลือก event-sourcing หรือ scheduler สำหรับงานนี้

คงความรับผิดชอบใน `school-staff` เป็น module ประวัติแยก DTO, validation และ SQL service ไม่สร้าง crate ใหม่ เพราะมี owner และ transaction เดียวกับข้อมูลบุคลากร และไม่มี dependency boundary หรือ compile-scope value ใหม่ที่พิสูจน์ได้

## ประเภทบุคลากร

เพิ่ม enum มาตรฐานที่ระบบดูแล: `civil_servant` (ข้าราชการครูและบุคลากรทางการศึกษา), `government_employee` (พนักงานราชการ), `contract_employee` (บุคลากรอัตราจ้าง), `permanent_employee` (ลูกจ้างประจำ), `other` (อื่น ๆ) และ null (ยังไม่ระบุ)

เลือกผ่าน dropdown แยกจากตำแหน่ง ไม่อนุมานจากชื่อ ตำแหน่ง บทบาทสิทธิ์ หรือประเภทการจ้างเดิม ข้าราชการที่เป็นครู ผู้ช่วยครู หรือผู้บริหารจึงใช้ประเภทเดียวกันแต่ตำแหน่งต่างกันได้ พนักงานโรงเรียนเอกชนหรือประเภทที่ยังไม่มีรหัสเฉพาะเลือกอื่น ๆ และใส่หมายเหตุได้ ไม่ถือว่าเข้าข่ายเกณฑ์ ก.ค.ศ. โดยอัตโนมัติ

ไม่เพิ่มหน้าจัดการรายการมาตรฐาน ไม่เพิ่มประเภทนี้เป็นกราฟใหม่ในงานประวัติ การคำนวณภายหลังต้องตรวจทั้งประเภทและตำแหน่ง ไม่ใช้ประเภทเพียงช่องเดียว

## โครงข้อมูลและกติกาประวัติ

เพิ่ม `staff_career_history` เป็นประวัติรายบุคลากร แยกชนิด `personnel_type`, `job_position`, `academic_rank` รายการหนึ่งเปลี่ยนข้อเท็จจริงหนึ่งชนิด โดยใช้ typed variant ของ API และข้อกำหนด SQL ที่บังคับ payload ให้ตรงชนิด:

- UUID รายการ, UUID บุคลากร, ชนิดข้อมูล และค่ามาตรฐานของชนิดนั้น; ตำแหน่งอ้างอิง catalog เดิม ไม่มี enum ตำแหน่งชุดที่สอง
- `effective_date` เป็น nullable calendar date; null หมายถึงยังไม่ทราบวันที่ ไม่ใช่วันที่นำเข้าหรือวันที่เริ่มงาน
- `order_date` และ `order_number` เป็น nullable วันที่ออกคำสั่งและเลขที่คำสั่ง แยกจากวันที่มีผล; คำสั่งย้อนหลังจึงมีวันที่มีผลก่อนวันที่ออกคำสั่งได้
- แหล่งข้อมูล `existing_record` สำหรับค่าที่ย้ายจากระบบเดิม และ `staff_entry` สำหรับรายการที่ฝ่ายบุคคลบันทึก; แหล่งข้อมูลไม่ได้หมายถึงผ่านการตรวจคุณสมบัติทางกฎหมาย
- หมายเหตุ, revision, created/updated timestamps และผู้บันทึก/ผู้แก้ ใช้ UUID ผู้ใช้ ไม่บังคับคัดลอกชื่อหรืออีเมลลงประวัติ

`staff_info` เพิ่มประเภทบุคลากรและ pointer ไปยังรายการปัจจุบันของแต่ละชนิด ตำแหน่ง/วิทยฐานะ/ประเภทใน projection ต้องตรงกับชนิด บุคลากร และค่าของรายการที่ pointer อ้างอิง ใช้ deferred database integrity guard เพื่อยอมให้เขียนสองส่วนใน transaction แต่ห้าม commit state ที่ขัดกัน Guard นี้เป็นข้อกำหนดข้อมูลถาวร ไม่ใช่ migration hook

การย้ายสร้างรายการเริ่มต้นเฉพาะตำแหน่งและวิทยฐานะที่ไม่เป็น null ของ staff_info เดิม รวมค่า `none` และ `not_applicable` โดยรักษาค่าตามจริง วันที่/คำสั่ง/ผู้บันทึกต้นฉบับเป็น null ประเภทบุคลากรยังไม่ระบุ แถวที่ไม่มีค่าไม่สร้างประวัติสมมติ

หลังใช้งาน ค่า null สำหรับชนิดใดหมายถึงยังไม่ระบุ หากล้างค่าที่เคยมี ให้สร้างรายการการเปลี่ยนเป็น null และเลื่อน pointer มาที่รายการนั้น ประวัติก่อนหน้ายังคงอยู่

### การบันทึกและแก้ไข

1. **เปลี่ยนข้อมูลปัจจุบัน:** สร้างรายการใหม่พร้อมวันที่/คำสั่งที่ทราบ แล้วอัปเดต projection และ pointer พร้อมกัน ไม่แก้ทับรายการเดิม ค่าเปลี่ยนแต่ยังไม่ทราบวันที่ยอมรับได้โดยแสดงสถานะข้อมูลไม่ครบ การแก้ไขต้องส่ง reference/revision ของรายการปัจจุบันที่อ่านมา (หรือ explicit null เมื่อยังไม่มีรายการ) ของแต่ละชนิดที่เปลี่ยน เพื่อกันแบบฟอร์มเก่าทับค่าปัจจุบันของผู้ใช้อีกคน
2. **เพิ่มประวัติย้อนหลัง:** ไม่เปลี่ยนข้อมูลปัจจุบันโดยอัตโนมัติ ถ้ารายการย้อนหลังมีวันที่หลังวันที่ของรายการปัจจุบันชนิดเดียวกัน ต้องปฏิเสธและให้ผู้ใช้ปรับรายการปัจจุบันก่อน เพื่อไม่เก็บ timeline ที่ขัดกัน ถ้ารายการปัจจุบันยังไม่มีวันที่ ให้รับประวัติได้แต่ยังคำนวณระยะเวลาของค่าปัจจุบันไม่ได้
3. **เติมวันที่หรือแก้รายการที่บันทึกผิด:** ส่ง expected revision และเหตุผลแก้ไข; เพิ่ม revision พร้อม audit old/new ใน transaction ถ้าเป็นรายการปัจจุบัน ให้ปรับ projection ให้ตรงกัน ถ้า revision เก่า คืน 409 และรักษา draft ให้ผู้ใช้โหลดข้อมูลล่าสุดก่อนลองใหม่ กติกา timeline ใช้กับการแก้วันที่และเปลี่ยนรายการปัจจุบันด้วย ไม่ยอมให้วันที่ปัจจุบันอยู่ก่อนประวัติย้อนหลังชนิดเดียวกัน
4. **ข้อมูลทั่วไป:** การแก้วุฒิ สาขา สถาบัน หรือช่องอื่นไม่สร้างรายการ career และไม่แตะ pointer การส่งค่า career เท่าเดิมไม่สร้างรายการซ้ำ วันที่ของชนิดที่ไม่ได้แก้ยังอยู่ครบ

ไม่เปิดการลบ/ยกเลิกประวัติรายรายการในงานแรก รายการผิดแก้ได้โดยมีเหตุผลและ audit การล้างข้อมูลปัจจุบันเป็นรายการใหม่ ประวัติไม่เป็น immutable archive ที่อยู่นอกนโยบายลบข้อมูลบุคลากรหรือ retention ของระบบ

ไม่รับวันที่มีผลหรือวันที่คำสั่งในอนาคตในงานแรก เพื่อไม่สัญญาว่าระบบจะเปลี่ยนตำแหน่งอัตโนมัติภายหลัง วันที่เท่ากันไม่สรุปว่ารายการใดใหม่กว่า ใช้ pointer ปัจจุบันที่กำหนดชัดเจนและเรียงด้วยเวลา/UUID อย่างคงที่ วันที่ย้อนหลังอนุญาตได้โดยไม่บังคับลำดับการเลื่อนวิทยฐานะ เพราะมีกรณีเปลี่ยนตำแหน่งและแก้คำสั่ง

ตำแหน่ง inactive/custom เดิมดูและคงได้ตามกติกาเดิม การเพิ่มหรือเปลี่ยนเป็นตำแหน่งใหม่ต้อง active/selectable การเติมวันที่ของรายการเดิมไม่เท่ากับกำหนดตำแหน่งนั้นให้คนใหม่

เลขที่คำสั่งสูงสุด 100 Unicode scalar values หมายเหตุและเหตุผลแก้ไขสูงสุด 1,000 ตัด whitespace รอบข้อความ ปฏิเสธ control characters และไม่เก็บข้อความช่องว่างล้วน วันที่รับเป็น ISO date แล้วแสดง พ.ศ. ตาม UI ไม่แปลง calendar date ผ่าน timestamp ที่ทำให้วันเลื่อน

## API, สิทธิ์ และการบันทึกธุรกรรม

- เพิ่ม typed `GET /api/staff/{id}/career-history` แบบ cursor pagination ขอบเขตสูงสุด 50 รายการ แสดงรายการปัจจุบันและข้อมูลสถานะใน response โดยไม่โหลดประวัติทั้งหมดใน profile
- เพิ่ม typed `POST /api/staff/{id}/career-history` สำหรับประวัติย้อนหลัง และ `PATCH /api/staff/{id}/career-history/{entryId}` สำหรับแก้รายการพร้อมเหตุผล/revision ไม่มี API แก้ catalog POST ใช้ UUID รายการที่ client สร้างครั้งเดียวต่อ draft เป็น idempotency identity; retry ของ ID/payload เดิมคืน acknowledgment เดิม ไม่สร้างรายการ/audit ซ้ำ ส่วน ID เดิมแต่ target/payload ต่างกันคืน 409 โดยไม่เปิดเผยรายการของบุคคลอื่น
- Create/update staff เดิมรับข้อมูล career ปัจจุบันพร้อมวันที่/คำสั่งผ่าน DTO ที่ชัดเจน ไม่รับทั้ง field แบนเก่าและ payload ใหม่เป็นสองช่องทางเขียน เมื่อเปลี่ยน contract ให้ย้าย consumers/generated artifacts ใน release เดียว ไม่ทำ alias/fallback ถาวร
- ข้อมูลปัจจุบันใน profile เพิ่มประเภท รายการอ้างอิง revision วันที่มีผล วันที่คำสั่งและเลขที่คำสั่ง เพื่อให้แก้ไขโดยไม่ต้องโหลดประวัติเต็ม
- การอ่านใช้ `can_read_staff_profile` ตาม own/organization unit/organization tree/school การเขียนใช้ permission เดิมและตรวจว่า target เป็นบุคลากร tenant เดียวกัน ไม่มี permission code ใหม่ ไม่มีประวัติใน public-profile
- ผู้มีสิทธิ์เขียนแต่ไม่มีสิทธิ์อ่าน profile ไม่ได้รับประวัติทั้งหมดจาก mutation response ส่งเฉพาะ typed acknowledgment และ reference/revision ที่จำเป็นต่อ action ไม่เปลี่ยนสิทธิ์อ่านโดยนัย
- ทุก mutation ล็อก staff-user row เดียวกับ CRUD เดิม ตรวจ revision และ target entry แล้วเขียนประวัติ/projection/audit ใน transaction เดียว audit ล้มเหลวต้อง rollback ทั้งการเปลี่ยน ไม่เก็บหรือ log เลขบัตรประชาชน เอกสารแนบ หรือ raw request
- ใช้ ApiResponse/ApiErrorResponse, OpenAPI และ TypeScript ที่ generate จากสัญญา ห้าม DTO ที่ใช้ arbitrary JSON สำหรับ payload ประวัติ
- ไม่เพิ่ม realtime payload ของประวัติ หลัง mutation ปรับเฉพาะ region ที่เกี่ยวข้องจากผล typed action แล้วอ่านข้อมูลผ่าน policy เดิม ไม่ invalidate identity หรือ workspace ทั้งหมด ไม่มีการแจ้งเตือนภายนอก

## หน้าจอ

**หน้าเพิ่ม/แก้บุคลากร:** เพิ่ม dropdown ประเภทบุคลากร ตำแหน่งและวิทยฐานะยังใช้ตัวเลือกเดิม แต่แต่ละช่องมีรายละเอียดวันที่มีผล/วันที่คำสั่ง/เลขที่คำสั่งแบบยุบได้ สื่อว่าช่องวันที่เว้นว่างได้เมื่อยังไม่ทราบ ไม่ prefill จาก hired_date เมื่อเปลี่ยนค่า ต้องเริ่มชุดรายละเอียดของค่าใหม่ว่างโดยไม่ส่งวันที่ของค่าเดิมตามไป

**หน้ารายละเอียด:** แสดงการ์ดตำแหน่งและวิทยฐานะปัจจุบันพร้อมวันที่มีผล และ section “ประวัติตำแหน่งและวิทยฐานะ” เป็น timeline/รายการตามวันที่ มี badge แยกชนิด ปัจจุบัน และไม่ทราบวันที่; วันที่ออกคำสั่งกับวันที่มีผลแสดงชื่อชัดเจน ไม่ใช้กราฟสำหรับรายการคำสั่งรายคน ปุ่มเพิ่มประวัติ/แก้รายการเป็น Button พร้อมไอคอนตาม UI ที่ปรับแล้ว

เพิ่มประวัติผ่าน dialog เลือกชนิดและค่า เลือกวันที่/คำสั่ง/หมายเหตุ แจ้งว่าการเพิ่มย้อนหลังไม่เปลี่ยนข้อมูลปัจจุบัน การแก้รายการมีเหตุผลบังคับและแสดงผลกระทบต่อข้อมูลปัจจุบันก่อนส่ง mutation ผู้ไม่มีสิทธิ์เขียนไม่โหลดข้อมูลสำหรับ action

Own profile อ่าน section เดียวกันได้ตาม scope แต่ไม่เพิ่มสิทธิ์เขียนเอง Directory และ Dashboard คงค่าปัจจุบันและกราฟเดิมในงานนี้ ไม่สร้างวันที่ยื่นหรือแสดงสถานะพร้อมยื่นก่อนงานคำนวณ

ใช้ PageShell, Card, Button, Input, Select และ dialog ของระบบ ให้ section ประวัติมี skeleton/error/retry/empty/load-more ของตนเอง ไม่บล็อกข้อมูล profile ที่โหลดสำเร็จ หน้าแก้ไขคง draft เมื่อ validation/server/conflict ผิดพลาด Dialog เปิดซ้ำไม่แอบส่งรายการซ้ำ ปุ่ม disabled ระหว่างบันทึก แต่ server ยังต้องกัน stale concurrent mutations ด้วย revision

Draft เพิ่มข้อมูล career เป็น schema version ใหม่ อ่าน v3 ของ owner เดิมที่ยังไม่หมดอายุเพื่อย้ายค่าปัจจุบันไป payload ใหม่และคงช่องอื่นทั้งหมดที่ schema เดิมยอมรับ โดยวันที่ทั้งหมดว่าง แล้วลบ key เก่าหลังย้ายสำเร็จ ไม่เดาประเภทบุคลากร ไม่เก็บ password/PII เพิ่ม และไม่ต่ออายุ draft เดิมเพราะการย้าย

ตรวจ desktop/mobile, light/dark, keyboard focus/label, error feedback และไม่มีลิงก์ข้อความขีดเส้นใต้แทนปุ่ม action

## Migration และการส่งมอบ

เพิ่ม migration ต่อจาก timeline ณ ลงมือจริง (ปัจจุบัน 085) ไม่แก้ 081–084 ใช้ tenant migration runner และ maintenance ของ release flow เดิม สร้าง schema/backfill/ตรวจ preservation ใน SQL transaction ไม่เพิ่ม personnel migration service, endpoint หรือ deploy gate เฉพาะกิจใหม่

ตรวจ exact equality ของค่า position/rank เดิมกับ projection และรายการปัจจุบัน รวม UUID บุคลากร/staff_info, null/enum/custom position และไม่มีรายการที่ได้วันที่สมมติ ตรวจ fields การศึกษา ใบอนุญาต employment_type/metadata/timestamps เดิมไม่ถูกแก้ unrelated updates การย้าย retry ผ่าน migration runner ต้องไม่ทำสำเนาหรือทิ้ง state บางส่วน

Provider rehearsal ใช้ disposable copy ของทุก tenant ที่ได้รับผลกระทบ และเตรียม recovery ก่อน promotion ตาม Operations ห้าม binary รุ่นเก่าซึ่งเขียนตำแหน่ง/วิทยฐานะโดยไม่ผ่าน owner ใหม่ทำงานหลัง cutover ถ้าตรวจไม่ผ่านคง maintenance และแก้ไปข้างหน้าด้วย release/migration ใหม่ ไม่ย้อนเฉพาะ application ให้ invariant เสีย

## เกณฑ์ตรวจรับ

1. Backfill รักษาค่าเดิมทุกแบบ ไม่มี hired_date/timestamp ถูกใช้เป็น effective_date ไม่มีการอนุมาน personnel_type และ provisioning ใหม่ใช้ migration chain เดียว
2. เปลี่ยนค่าปัจจุบันพร้อมวันที่/คำสั่ง เพิ่มย้อนหลัง เติมข้อมูลเดิม แก้รายการผิด และล้างค่าได้โดยประวัติ/projection/pointer/audit ตรงกันเสมอ
3. วันที่อนาคต รูปแบบวันที่ผิด payload ผิดชนิด ชี้ entry ของคนอื่น/ชนิดอื่น timeline ขัดกัน และ revision เก่าถูกปฏิเสธ Transaction/audit failure ไม่ทิ้งข้อมูลครึ่งหนึ่ง
4. Direct profile updates ผ่าน owner ใหม่ การส่ง career ไม่เปลี่ยนค่า หรือแก้ช่องอื่นไม่สร้างประวัติซ้ำ ไม่เอาวันที่ของ rank เก่าไปเป็นวันที่ของ rank ใหม่ Concurrent append/correction ปลอดภัย
5. Own/unit/tree/school profile scope และ mutation permissions ครอบคลุม allowed/denied paths directory/dashboard counts ยังตรงกัน ไม่มี leak ผ่าน public profile, mutation response หรือ realtime
6. Browser ครอบคลุมสร้าง/แก้/อ่าน เพิ่มย้อนหลัง การแก้เหตุผล/409 retry วันที่ว่าง/ภาษาไทย การรักษา draft/draft upgrade, pagination, regional errors, theme/responsive และ read-only user
7. รัน focused domain/transaction/schema/policy tests และ matrix ที่เกี่ยวข้องของ backend-school, generated API, frontend ตาม `.rules`/Testing พร้อม provider rehearsal, CI/release และ deployed read-only acceptance ก่อนกล่าวว่าส่งมอบแล้ว

## งานคำนวณที่ต่อจากประวัติ

Specification ถัดไปต้องตรวจหนังสือฉบับเต็มและการแก้ไขที่มีผล ณ ส่งมอบ แล้วกำหนดกติกาที่มี version, ขอบเขตวันที่ใช้บังคับ, หลักฐานเงื่อนไขลดระยะเวลา และสูตร calendar date เริ่มที่ข้าราชการครูสายการสอนตามที่ตกลง ไม่ใช้วุฒิปริญญาโทหรือชื่อครูอย่างเดียวเป็นหลักฐานผ่านเกณฑ์

ต้องแยก “วันครบระยะเวลาขั้นต่ำ” จาก “คุณสมบัติครบสำหรับยื่น” และรองรับข้อมูลไม่ครบ/เกณฑ์ไม่รองรับ/รอตรวจ พร้อมการ์ดและตาราง Dashboard ใกล้ครบ 90 วันตาม scope เดิม ไม่ใช้วันที่นำเข้าประวัติเป็นจุดเริ่มนับ และไม่แสดงข้อความพร้อมยื่นจากวันที่เพียงอย่างเดียว
